## How to read a row

- **The rule** is in plain words. Rust terms get a one-line gloss the first time they appear.
- **Enforced by** names the tool:
  - **rustc** is the compiler.
  - **clippy** is Rust's linter, the ESLint of Rust. **clippy.toml** is its config file, whose ban lists (`disallowed-types`, `disallowed-methods`, `disallowed-macros`) work like ESLint's `no-restricted-imports` and `no-restricted-syntax`.
  - **ast-grep** is a pattern matcher over the syntax tree, like a custom ESLint rule written as a pattern.
  - **cargo-deny** checks the dependency list, like `npm audit` with a ban list.
  - **CI**, a **script** in `engine/tools/`, the **guard** (the hook that refuses edits) and **review** are the rest.
- **Levels.** CI fails on any warning (`-D warnings`), so a clippy rule is either an error or off. There are three levels:
  - **error, no exception:** Rust's `forbid` level. No attribute in the code can switch it off, like an ESLint rule with `noInlineConfig`.
  - **error:** an exception is possible only as a counted, reasoned `#[expect(lint, reason = "…")]` on the smallest piece of code. That is Rust's version of `// eslint-disable-next-line rule -- reason`, except the compiler fails if the problem goes away and the exception stays.
  - **report:** never fails CI. The exception counter lists every hit for the audit.
- **Evidence:** a named real project that does this, the tool's docs, or "untested" (my proposal).
- **Your answer** is empty until gate 1.
- **An amended row** keeps its old text and adds **Amended <date> (G1 item n; source):** with the change, in the rule's cell and, where they change, in the bug, cost and enforcement cells ("Since <date>: …"). Its answer cell keeps the old answer and adds the new one. A row raised from report-only shows both in its Rec. cell ("report → keep").
- **A new row** (R-114 onwards) says **New <date>** at the start of its rule, and its answer cell holds the user's words at G1 as `tmp/session8/decisions.md` records them.
- A ⚖ marks a row where the research agents disagreed. The row states the other side, and `NOTE.md` §2 has the settlement.
- Every rule that a tool enforces gets a planted violation in `rules-selftest`, which must fail with that rule's name (brief §7.3).

## 1. Panics and crashes

A **panic** is a deliberate crash: the Rust version of an uncaught `throw` that ends the process. In this engine a crash on a user's model is always a bug. The spec wants a coded refusal instead (ENGINE §9, l.387: an invariant failure refuses the result with `ENGINE-INVARIANT`).

## 2. Numbers and money

Tally's numbers are exact fractions, capped at 4,096 digits (`RUN-DIGITS`), with division by zero refused (`RUN-DIV`) and no floating point anywhere (LANGUAGE §7.1, l.1449–1451). The engine wraps a big-integer crate in its own `Num` and `Money` types. Their methods return a refusal instead of crashing. This group keeps every other route to a number closed. **Since tally 2.1** (rows R-114 to R-117, added 2026-10-30) it also covers the values 2.1 adds around numbers: parts and their splits (L §3.6), holes and hole parts (seam U), and a path statistic's accumulation (L §7.1).

## 7. Exceptions policy (brief §5.2)

Strictness fails when a rule blocks real work and the LLM routes around it. So an exception must be possible, visible, explained, counted and bounded.

### 7.1 The policy in plain words

- **How it is written.** An exception is `#[expect(clippy::<lint>, reason = "R-<n>: <why it is safe here>")]` on the smallest item, statement or expression.
  - It is Rust's `// eslint-disable-next-line <rule> -- <reason>`, with two differences. The reason is part of the attribute, so a tool checks it. And if the code stops breaking the rule, the exception itself becomes an error, so it can't go stale.
  - `#[allow]`, the silent form, is never used.
  - This replaces C's `-- Reason:` comment for Rust code. The repo's ESLint convention stays as it is for TypeScript.
- **Where it is allowed.**
  - Never on a rule of the "no exception" level (R-106).
  - Never on a whole module or file (R-107).
  - Exceptions to the ban lists (I/O, threads, big integers) only in files the lead sanctions (R-108). At the scaffold that is only the CLI's `main.rs`; the merge module and the number kernel's files are added when the builder names them.
  - Tests get their freedoms from config (`unwrap`, indexing and asserts allowed in test code), not from exceptions.
- **How it is counted.**
  - `engine/tools/exceptions` finds every exception form and prints its count, file, enclosing item, lint and reason, by area (number kernel, rest of the library, CLI, tests, fuzz and benches). It prints 0 on the stubs.
  - `--check` compares the result with the committed `engine/EXCEPTIONS.lock` and fails on any difference. `--write` regenerates the lock, and the builder commits it with the code, so each new exception is a one-line diff.
  - A protected budget (`engine/tools/exceptions-budget.toml`) caps each area. Going over turns CI red, and the builder files a STOP-REPORT.
- **What the audit does with the count.**
  - At each milestone the reviewer reads every lock entry added since the last tag. It judges whether the reason is about the domain ("the index is below the length because the loop guard checks it") or about quieting a tool ("clippy false positive", "for now").
  - You see the count and the reasons in plain words.
  - A rising count outside the number kernel is a finding.
  - A budget rises only with your dated approval, recorded in this rulebook.
- **Proposed starting budgets** (you set them at this gate):
  - rest of the library: 0;
  - lexer and parser: 0, which gleam shows is possible;
  - CLI: 3 (arguments, reading the reality, writing output);
  - thread module: 1;
  - number kernel: one per arithmetic function, at most 20 at S, reviewed after S.
  - For scale, cedar runs at 3–7 per 1,000 library lines.
- **Approved budgets** (the user, 2026-10-22): as proposed above. Raising one needs the user's dated approval here.

Rust terms used here, once:

- a **trait** is an interface; a **`dyn` trait** (a trait object) is a value whose concrete type is picked at run time, like calling a method through an interface-typed variable in TypeScript;
- a **generic** (a type parameter) is TypeScript's `function f<T>(x: T)`;
- an **`impl Trait` argument** is a parameter typed only by an interface, `fn f(x: impl Iterator<…>)`, a generic in disguise;
- a **lifetime** is an annotation telling the compiler how long a borrowed reference stays valid;
- a **newtype** is a one-field wrapper type, like a TypeScript branded type (`number & { __brand: 'Day' }`), which compiles down to the bare value;
- **`//!`** starts a file-level doc comment, like a JSDoc `@file` block.
