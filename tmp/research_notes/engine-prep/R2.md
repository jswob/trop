# R2: data and numbers at speed

**Question.** How should the engine hold its numbers and its data so that it is fast, exact, deterministic and inside the 8 GB cap, while staying buildable under phase 1's rules and readable by its owner? The seven sub-questions are in `tmp/session8/agents/R2/brief.md`.
**Date:** 2026-10-30. **Agent:** R2 (session 8, part A). Paper only. Nothing was run except `python3 -I -c` arithmetic shown in the text.
**Inputs:** `tmp/session8/shape.md` (whole); A3 §2, §3, §5, §7; NOTE §1 items 3 and 14, K-11, K-12, SO-12..24; RULEBOOK groups 2–3; BUILDER §2, §3, §7; PERFORMANCE §6 and §9; LANGUAGE §3.1, §3.6, §7; BUILD-NOTES; `tests/load/benchmarks.md`, `load.tsv`; the scaffold's `deny-tally.toml` and `Cargo.toml` (read only).

## Summary

1. **Numbers: keep R-30's crate, and change the tiers.** num-bigint 0.4.8 is still the right base: it is permissive, fuzzed, and every alternative is worse on licence, unsafe code or track record (crates.io, 2026-10-30). shape.md's distribution backs a **two-tier `Num`**: `Small` (i64/i64 inline) and `Big`. There is **no i128 tier**. Almost every result above 63 bits is above 1 024 bits (E1: 1 693 results over 1 024 bits against about 1 664 over 63 bits), so an i128 tier would hold almost nothing. i128 stays as the intermediate of cross-multiplication. Add an **integer fast path**: when d = 1, which is 77–99 % of results, skip every gcd. Target 16 bytes for `Num` (inference: a compile settles it).
2. **gcd: write Lehmer now, not "if a benchmark asks".** GMP, CPython, malachite and dashu all use Lehmer at Tally's sizes. num-bigint alone uses Stein (`biguint.rs`, master, 2026-10-30). GMP switches to half-gcd only above 618 limbs (Skylake) or 330 limbs (arm64), while the cap is 213 limbs. So **Lehmer is the top algorithm Tally ever needs, and half-gcd never pays below the cap.** E1 reaches 5 049 bits on a real household check. Without Lehmer, the engine's balanced gcds there are slower than those of refcore's own Python (inference from A3 F-3's counts).
3. **Money: a whole number of minor units, `I64 | Big`.** The spec makes money whole minor units by type (LANGUAGE §3.1). A rational appears only where §7.2 says money has left the money type: money × num, money ÷ anything, shares, prorata, path statistics, and `num CUR` defs that are never rounded (which is how E1 grows). Money + money is one checked i64 add, with no gcd. Drop phase 1's i128 money tier: no household value comes near 9.2·10¹⁶ zł.
4. **Interning pays, but for key values, not for parsing.** Memo keys hold key values: things, keys of open indices, labels. Making them `u32` symbols makes a memo key fixed-size and cheap to compare. Follow rustc: a `Symbol(u32)` whose output order is **by its text** (`StableCompare for Symbol` compares `as_str()`, rustc master, 2026-10-30). That honours R-47. Write it by hand, about 50 lines. lasso and string-interner both depend on hashbrown, which `deny-tally.toml` bans outside indexmap. This replaces BUILDER §3's "no interner".
5. **Ids and tables: an own `Table<I, T>` with `get` only and no `Index` impl.** Indexing would panic, and `get(id)?` costs the same bounds check (Readyset measured the checks as negligible, 2026-10-30). No arena crate: each adds a dependency to R-52's allow-list for about 40 lines of work, and their `Index` impls are what R-5 forbids.
6. **Collections: B-trees by default, dense tables for the hot memo, no hash map.** shape.md finds a few defs keyed by day carrying 85–95 % of the memo misses. A **dense table per def, indexed by key position**, is O(1), deterministic, and stores no key. BTreeMap covers the sparse rest; frozen tables are sorted boxed slices searched by bisection. A hash memo with a fixed hasher and no iteration (rustc's `UnordMap` design) is held back as a G1 option, because it needs an R-36 exception.
7. **Overlays: no persistent-map crate.** Pins and scenarios are bounded (at most 4 + 4 layers), so they become small sorted layers inside an interned context id. Walk checkpoints are `Vec<Rc<PlaceState>>`, cloned in O(places) and copied on write with std's `Rc::make_mut`. `im` is unmaintained and has an unsound advisory (RustSec, 2026-10-30). `imbl` pulls `rand_core` and `rand_xoshiro` into what ships.
8. **Memory is inside 8 GB at every measured size, if the memo is scoped per context.** Estimates (inference): about 70–90 B per sparse memo cell and 24–32 B per dense cell, against refcore's 2 180 B/cell (X: 4.95 GB / 2.27 M). Also about 64 B per row, about 100 B per two-leg movement, and about 40 B per booked leg. X's memo would take about 0.2 GB. B-07's 83 GB, divided by about 25, gives about 3.3 GB *if nothing is freed*, but that run was stopped and never finished. Per-context memos (one per search step and per path), freed when the context ends, are the safeguard. Only the engine can measure it (G1).

**Decisions:** D2-1 the number tiers and the gcd · D2-2 money · D2-3 interning · D2-4 ids and tables · D2-5 the collections policy · D2-6 walk storage and overlays · D2-7 the memo's shape and scope.

## Findings

### Q1. Exact rationals with a small-value fast path

**How the prior art holds small values.**
- **FLINT `fmpz`**, the closest prior art: one machine word. If its two top bits are equal, the word *is* the integer, up to ±(2^62 − 1). Otherwise the word holds a pointer to a GMP `mpz`. The form is canonical: "A value that fits inline is always stored inline", and `_fmpz_demote_val` moves a value "back inline if it fits". The point: "small values cost no memory allocation and most operations on them run without a function call into GMP" (flintlib.org/doc/fmpz/index.html, fetched 2026-10-30). This is phase 1's `Num` invariant ("Small whenever the value fits", BUILDER §2) with a 40-year-old precedent behind it.
- **GMP `mpz`/`mpq`** has no inline tier: every value has its own limb array, and `mpq` is kept canonical. Small values are FLINT's addition on top of GMP (inference from the fmpz doc above).
- **CPython ints:** 30-bit digits. A value of at most one digit is "compact" (`_PyLong_IsCompact`: `lv_tag < (2 << _PyLong_NON_SIZE_BITS)`), and the arithmetic takes a fast path on compact values (`Include/cpython/longintrepr.h`, `Objects/longobject.c`, main, fetched 2026-10-30).
- **CPython `fractions`:** Knuth TAOCP 4.5.1, which skips the second gcd when the first is 1 (`_add`: `g = math.gcd(da, db); if g == 1: …`; `Lib/fractions.py`, main, fetched 2026-10-30).
- **Java `BigDecimal`:** keeps `long intCompact` for unscaled values of up to 18 digits, and inflates past that (OpenJDK `BigDecimal.java`, fetched 2026-10-30). The same two-tier idea, applied to decimals.
- **malachite:** `enum InnerNatural { Small(Limb), Large(Vec<Limb>) }` (`malachite-nz/src/natural/mod.rs`, master, fetched 2026-10-30).
- **num-bigint:** has inlined single digits since 0.4.7 (RELEASES.md, fetched 2026-10-30).
- **dashu:** up to 2 words inline (A3 §3.1 [S9], fetched 2026-10-22).
- **Ledger** (plain-text accounting): every amount is a heap `mpq_t`, with no small tier (`src/amount.cc`, fetched 2026-10-30). This is prior art for exact rationals in bookkeeping, and also for paying the heap cost on every value when there is no small tier.

**The gcd algorithms, and where each wins.**
- **Stein (binary).** num-bigint's `BigUint::gcd` is still "Stein's algorithm" on master (`src/biguint.rs`, fetched 2026-10-30). On machine words, a good binary gcd beats Euclid about 2× (91 ns against 198 ns per random gcd; en.algorithmica.org/hpc/algorithms/gcd/, fetched 2026-10-30). On big values it is O(n²) in *bit* steps. A3 F-3 counted 2.4·10⁵ word operations at 1 406 digits.
- **Lehmer.** CPython's `_PyLong_GCD` uses Lehmer above 2 digits, with a simple loop at 2 digits or fewer (`longobject.c`, fetched 2026-10-30; bpo-22486). GMP uses Lehmer up to `GCD_DC_THRESHOLD`: "Once the input numbers are reduced to size below GCD_DC_THRESHOLD, Lehmer's algorithm is used for the rest of the work" (gmplib.org/manual/Subquadratic-GCD, fetched 2026-10-30). malachite and dashu use Lehmer too (A3 F-3, F-7).
- **Half-gcd (subquadratic).** O(M(N) log N) (same GMP page). Its threshold is `GCD_DC_THRESHOLD` = **618 limbs** on Skylake and **330 limbs** on arm64, from tuned `gmp-mparam.h` (2019 tunings, read from the GitHub mirror alisw/GMP on 2026-10-30, because gmplib.org's repository refused the fetch with a 403). That is 39 552 and 21 120 bits.
- **Tally's sizes.** The cap is 13 606 bits = **213 limbs**, and E1's largest result is 5 049 bits = **79 limbs** (`python3 -I -c 'print(13606/64, 5049/64)'`). So GMP itself would never leave Lehmer inside Tally's cap: **half-gcd is not needed, and Lehmer is the ceiling.**
- **What that means for num-bigint (inference).**
  - A3's mod-first trick handles big × small: one short division, then a u64 gcd.
  - Two *balanced* big values still go through Stein. That happens when two big denominators meet, as in a sum of two compounded values.
  - CPython's Lehmer took 25 µs at 1 400 digits. Stein is estimated at 0.05–0.3 ms (A3 M2, F-3). So on E1's big values, an engine on plain Stein would do balanced gcds slower than the oracle it must beat.

**What fits shape.md's distribution.**
- Over 99.9 % of results fit 64 bits, and 77–99 % are integers (shape.md).
- The values that leave 64 bits leave it far behind. E1 has about 1 664 results over 63 bits (0.08 % of 2.08 M) and 1 693 over 1 024 bits, so practically every escapee is already past 1 024 bits (the rounding of "99.92 %" puts the first figure between 1 560 and 1 768).
- So **an i128 rational tier would catch almost nothing**. A3 §5's own design already uses i128 only for intermediates (cross-products), which is where it belongs.
- **The integer path is the hot one (inference):**
  - when both denominators are 1, `+ − ×` is one `checked_*` on i64 with no gcd;
  - Knuth's add does `gcd(1, 1)` and exits, but an explicit `d == 1` branch makes that visible and testable;
  - short decimals (A: 7.2 %; E1: 20 %) have denominators that divide 10⁶, whose gcds end in a few steps.
- **Size.** `enum Num { Small { n: i64, d: NonZeroU64 }, Big(Box<BigRat>) }` can be **16 bytes**. Since 2022, rustc fills a niche even when several variants hold data (rust-lang/rust PR #94075, merged 2022-09-08, fetched 2026-10-30): the zero of `d` can tag `Big`. Layout is not guaranteed, so a `const` assertion of the size settles it at the first compile (inference). At 24 bytes nothing breaks; only the memo grows by about a third.

**LGPL for a shipped binary.**
- LGPL-3.0 §4 lets a Combined Work be conveyed under the author's own terms only if it also either (d0) conveys "the Minimal Corresponding Source … and the Corresponding Application Code in a form suitable for … the user to recombine or relink the Application with a modified version" of the library, or (d1) uses "a suitable shared library mechanism" (SPDX `LGPL-3.0-only.txt`, fetched 2026-10-30).
- Rust links crates statically and has no stable ABI for a Rust dynamic library (inference, common knowledge). So d1 is impractical, and d0 means shipping the engine's object code or source with every binary.
- The duty arises on conveying. A private app that is never distributed owes nothing. A template others copy would carry the duty (A3 §3.4 said the same).
- On top of that, malachite's hard dependency on libm breaks K-8.

**Panics and checked APIs.** These are unchanged from A3 F-2, F-5 and F-17. Every candidate needs the engine's wrapper, so the wrapper owns the tiers.

### Q2. Money at a fixed minor unit

- **Whole minor units is the spec, not luck.** `money CUR` is "a whole number of minor units", and a finer literal is refused (LANGUAGE §3.1, `LOAD-PRECISION`). "A `num CUR` becomes money only through `round` … or `prorata`" (§7.2). So shape.md's "every money value a whole number of cents" is guaranteed by the type. What shape.md adds is that the *values* never approached 64 bits.
- **Where a rational must appear** (all from the spec):
  1. money × num: a rate, a share, a factor, a parts share (§3.6's arrival rule: "each owner's part its share of it"). The result is `num CUR` until a `round`.
  2. money ÷ money, which is a dimensionless share, and money ÷ int or num.
  3. `prorata` and the parts splits: exact quotients, then `rest largest` to the step (§3.6, §5.13).
  4. path statistics: an exact mean or variance, unbounded by the cap (§7.1, R-13).
  5. a `num CUR` def that is never rounded: an accrual or a compounding balance. This is how E1 reaches 5 049 bits (inference: shape.md names `mtg_bal`, `principal_on` and `ov_fee` among its top defs).
- **What it costs (inference).**
  - money ± money: one checked i64 add, about 1 ns, with no gcd. Holding money as a reduced rational would cost a gcd per add, because 123456/100 reduces to 30864/25 and every later add must find the common denominator again.
  - money × rate p/q with a short-decimal q: an i128 product and a gcd of small numbers, tens of ns.
  - `round` straight after: a floor division of the numerator by q × step, plus a remainder test for the mode. That is O(size), and needs no gcd on an already-reduced value.
  - Fusing "multiply, then round" into one step without reducing in between is possible later. It is invisible except through `RUN-DIGITS` (SO-12), so it is an optimisation to take only if measured.
- **Tiers: drop i128 for money.**
  - i64 minor units reach 9.2·10¹⁶ zł.
  - An i128 tier adds a variant, a widening path and mutants (gate 8) for values no case reaches.
  - Not observable in results: A3 §7 item 9 says the same.
  - PERFORMANCE §6 says "widened to 128 bits", but it is a cost note and stale (STALE.md).

### Q3. String interning (seam N)

- **rustc:**
  - `pub struct Symbol(SymbolIndex)`, a u32. The interner is an arena plus a hash table and a `Vec` of strings (`compiler/rustc_span/src/symbol.rs`, master, fetched 2026-10-30).
  - It derives `Ord` on the index, but anything whose order must be stable uses `impl StableCompare for Symbol { fn stable_cmp(..) { self.as_str().cmp(other.as_str()) } }`. That is R-47's rule in the compiler's own code: ids are for identity, text is for order.
- **rust-analyzer:** `intern::Symbol` is a tagged `Arc` pointer in a global `DashMap`, freed at run time (`crates/intern/src/symbol.rs`, fetched 2026-10-30). That is concurrency machinery an engine with one load phase doesn't need.
- **ruff:** doesn't intern names in the tree. `Name` is a 16-byte `CharStr`, inline up to 16 bytes and shared by reference count above that (`ruff_python_ast/src/name.rs`, fetched 2026-10-30). ruff's type checker interns at its Salsa boundary (same file's note).
- **The crates are blocked by R-37 as built.**
  - lasso 0.7.3 (2024-08-19) and string-interner 0.20.0 both depend on hashbrown (crates.io dependencies API, 2026-10-30).
  - `deny-tally.toml` allows hashbrown only under indexmap.
  - string-interner also has RUSTSEC-2019-0023 (old, patched).
- **Does interning pay here? Yes, at run time, for key values (inference).**
  - Seam F's memo key holds key values. Things and keys of open indices are text ids, and so are labels (§3.6).
  - With symbols, a key is a few u32s, so the memo key is fixed-size and comparing it is a few integer compares.
  - With `Box<str>`, every memo probe compares strings, and every cell owns or points to one. At X's 4.55 M memo probes that is the difference that matters.
  - At load the gain is small. BUILDER §3's `BTreeMap<Box<str>, ItemId>` is fine there.
- **Deterministic by construction.**
  - Intern in load order: files sorted by name bytes (R-40), then text order. The same reality gives the same ids on every run.
  - Never print or sort output by id: output sorts by `as_str()`, as rustc does.
  - Seam N's table is then `BTreeMap<(PathId, Sort, Symbol), Entry>`, all small integers.

### Q4. Arenas and index-based graphs

- **rustc** uses `IndexVec<I, T>` with `newtype_index!` ids (u32). **rust-analyzer** uses `la_arena::Idx<T>` (a `RawIdx(u32)`) with `impl<T> Index<Idx<T>> for Arena<T>`, which panics on a bad id and has no inherent `get` (`lib/la-arena/src/lib.rs`, fetched 2026-10-30).
- **The lint.** clippy's `indexing_slicing` (master) fires on slices, arrays, and an ADT whose inherent `get` returns `Option` of the indexed type or a type parameter (`ty_has_applicable_get_function`, `clippy_lints/src/indexing_slicing.rs`, fetched 2026-10-30). This widening arrived in Rust 1.88, when `match_on_vec_items` was folded into it (CHANGELOG, #14217).
  - la-arena has no `get`, so its indexing stays invisible, as A2 found.
  - Whether `TiVec` or `IndexVec` indexing is caught depends on that heuristic, and only a compile settles it.
  - **A type with no `Index` impl can't be indexed at all.** That is the only airtight form.
- **The crates on 2026-10-30:**
  - typed-index-collections 3.5.0 (MSRV 1.90) and index_vec 0.1.4 (2024) both implement `Index`.
  - id-arena 2.3.0.
  - slotmap 1.1.1, Zlib: generational keys for deletion, which the engine's load-time tables never need. Per-context memos are freed whole.
  - la-arena 0.3.1 (last code release 2023).
  - Each would be a new entry on R-52's allow-list.
- **What the safe accessor costs.** `table.get(id).ok_or(Internal)?` is the same bounds compare that `[]` does, plus a `Result` branch that is never taken.
  - Readyset removed half of a hot path's 1 227 bounds checks, then all of them with a patched rustc. The difference was within noise: "the cost of pervasive runtime bounds checking is negligible" (readyset.io/blog/bounds-checks, fetched 2026-10-30).
  - The real loss is blocked vectorisation in tight numeric loops (same source). The engine's tables are indirect lookups, which don't vectorise anyway (inference).
- **Ids are u32,** half the memory of `usize`, and fixed width as R-44 asks. The conversion to `usize` goes through `usize::try_from`, which the optimiser folds away on 64-bit targets (inference).

### Q5. Compact storage, and overlays

- **Array of structs by default.** For the 2–3 logs that are searched by day (a place's booked legs, change points, the walk's checkpoints), keep a **separate `days: Vec<i32>` column** beside the payload. The search is then a bisection over 4-byte integers, which is cache-dense. That is struct-of-arrays only where a search runs (inference).
- **Small vectors: std only.**
  - smallvec 1.16.4 has five RustSec advisories, among them RUSTSEC-2021-0003, a buffer overflow in `insert_many` (patched).
  - tinyvec 1.13.3 has none and forbids unsafe, but it needs `Default`, and R-28 bans `Default` on `Num` and `Money`.
  - arrayvec 0.7.8 has none (RustSec advisory-db, fetched 2026-10-30).
  - So use `Vec`, and `Box<[T]>` once frozen. Revisit only if a profile shows allocation.
- **Parts** (§3.6; BUILD-NOTES "the labels' cost").
  - Per (place, unit): a sorted `Vec<(Label, Money)>`, with `Label` = (owner `Symbol`, batch `MovementId`) packed to 8 bytes, so about 24 B per live label.
  - Arrival and take are a bisection plus an insert, O(L) moves. That is within the spec's O(L log L) for L live labels.
  - A place that keeps no parts holds one `Money` per unit, with no `Vec` at all, as seam "labels" asks (inference).
- **Persistent maps** (RustSec and crates.io, 2026-10-30):
  - `im` 15.1.0: last release 2022; **RUSTSEC-2026-0248 unmaintained** and RUSTSEC-2023-0126 unsound in `OrdSet`. Drop.
  - `imbl` 7.0.2: MPL-2.0. It depends on `rand_core` and `rand_xoshiro` unconditionally (its Cargo.toml), a random-number family in what ships, against R-41's intent.
  - `rpds` 1.2.1: MIT, depends on archery and smallvec. Clean, but a new dependency.
- **None is needed (inference).**
  - **Pins and scenarios** are bounded: `LOAD-SCENARIO` and `LOAD-ASIF` allow at most 4 each. So an overlay is a stack of at most 8 small sorted layers, read top-down, and the stack is interned into the context id of seam F.
  - **Walk checkpoints** (PERFORMANCE §4.2; shape.md point 3: 64×, 8–12× and 20× repeats of one walk): `Vec<Rc<PlaceState>>`. A checkpoint clones the outer `Vec`, which is O(places) pointer copies. A booking calls `Rc::make_mut`, which "will clone the inner value … also referred to as clone-on-write" (doc.rust-lang.org Rc::make_mut, fetched 2026-10-30).
  - That is path copying at one level, std only, and deterministic. `Rc` stays inside one worker; a checkpoint shared across R-42's workers would be `Arc`.

### Q6. Maps with a deterministic order

- **BTreeMap.** It searches nodes linearly, about B·log n comparisons, "excellent performance on small nodes of elements which are cheap to compare" (std docs, 1.99.1, fetched 2026-10-30). Integer keys made of symbols are exactly that case.
- **Hash maps are faster for point lookups.**
  - rustc found that going from FxHasher back to the default hasher slowed it by 4–84 %, and FxHasher "out-perform[s] all other hash algorithms within rustc" (nnethercote.github.io/perf-book/hashing.html, fetched 2026-10-30).
  - rustc keeps them deterministic by API rather than by hasher: `rustc_data_structures::unord` gives "collection types that don't expose their internal ordering", whose `UnordItems` offers only order-free operations (`unord.rs`, master, fetched 2026-10-30).
  - clippy's `iter_over_hash_type` sees only `for` loops over std `HashMap`/`HashSet` (its source, fetched 2026-10-30), so a lint can't guard such a map's iteration. Only its API can.
- **IndexMap** 2.14.2 depends on hashbrown, which `deny-tally.toml` already allows only under indexmap. Insertion order is deterministic whatever the hasher.
- **A dense table beats every map where the key is a position (inference).**
  - The hot memo cells are defs keyed by a day or a period (shape.md: A 85 %, X 95 % of misses).
  - `Vec<Slot>` indexed by (key position − first) is O(1), stores no key, and has no order question at all.
  - That reduces the memo's hard case to an array, the solved form of dynamic programming over an index.

### Q7. Memory against the 8 GB cap (all inference; sizes assume the layouts above)

| Unit | Estimate | Basis |
|---|---|---|
| `Num`, `Money` | 16 B (24 B if the niche fails) | Q1 |
| `Value` (Num, money, key, date, hole pointer, …) | 24–32 B | a tag plus the largest variant |
| memo cell, dense | 24–32 B | value only; the key is the position |
| memo cell, sparse (BTreeMap) | 70–90 B | key (def u32, context u32, up to 3 key u32s), plus a value, × about 1.4 for node fill |
| input row | about 64 B | keys 16, value 24–32, version and known/governs days 12 |
| movement with 2 legs | about 100 B | day, kind, id, legs (from, to, unit, money) |
| booked leg in a log | about 40 B | day, movement, delta, balance after |
| live parts label | about 24 B | Q5 |
| big value at E1's max | about 650 B | 79 limbs + header; 1 109 such values is about 0.7 MB |
| Monte Carlo path | its context's memo, freed after the path; kept: one `Value` per figure (D-10: 10 000 × figures × 24 B) | LANGUAGE §7.4: "a path is a pure function of its seed and number" |

- **At the measured sizes:**
  - X's 2.27 M cells come to 0.07–0.2 GB, against refcore's 4.95 GB (2 180 B/cell, `python3 -I -c 'print(4.95e9/2.27e6)'`).
  - A's 49 664 legs come to about 2 MB.
  - D-10 holds 6 path memos at once (one per worker) plus 10 000 result rows.
- **B-07** (83 GB, stopped at 4 635 s with nothing printed): a ratio of about 25 gives about 3.3 GB *if every cell were kept*. But the run never finished, so its total is unknown. A search of 4 001 steps, each a pin context, is the case for **freeing a context's memo when the context ends**. It is safe because the memo is pure (seam F).
- **The engine makes fewer cells than refcore** (skipped empty days, shared prefixes; shape.md "Limits"). So these are upper bounds per unit, not totals.

## What this means for Tally's engine (plain words)

- **Numbers** are a small box, `Num`.
  - Ordinary values (almost all) sit inside it as two 64-bit integers, like a JS number but exact.
  - A rare giant spills to the heap through a big-integer crate (an npm package; here num-bigint).
  - Integers skip the "reduce the fraction" step entirely.
- **Money** is an integer count of grosze.
  - Adding money is adding integers.
  - Multiplying money by a rate gives a fraction, and the compiler won't let it become money again until a `round`. That is Rust's type check doing the job of LANGUAGE §7.2, like a TypeScript branded type you can only create through one function.
- **Names become numbers once, at load.** That is a symbol table, like the strings-to-ids map a bundler builds. They are compared as numbers, and always printed and sorted by their text.
- **Tables are arrays reached by typed ids,** like a `Map<ItemId, Item>` where `ItemId` can't be mixed up with `RowId`. A lookup returns a `Result`, a typed error you must handle like a rejected promise, never a crash.
- **The memo** (the cache of computed cells) is an array where the key is a day or a period, and a sorted tree map elsewhere. Each scenario, search step or path gets its own memo, thrown away when it ends. That keeps memory flat.
- **No new crates are needed** beyond R-30's number stack.

## Decisions for the user

**D2-1. The number tiers and the gcd** (may amend R-30 and BUILDER §2).
- *Problem.* Phase 1 kept Stein's gcd and wrote Lehmer only "if the benchmarks ask". E1, a real household check, already makes 1 109 values over 4 096 bits.
- *Options.*
  - (a) Phase 1: num-bigint, Stein plus mod-first.
  - (b) **num-bigint, with the engine's own Lehmer gcd for big balanced values, plus mod-first.**
  - (c) Switch to dashu (Lehmer built in; 91 unsafe lines; 2026 wrong-result fixes).
  - (d) malachite (LGPL-3.0-only, and it depends on libm).
- *Recommended:* **(b)**, with `Num = Small(i64/i64) | Big`, no i128 tier, a `d == 1` fast path, and a size assertion of 16 bytes.
- *Cost:* about 150–250 lines of Lehmer, differential-tested against `num_integer::Integer::gcd` and Python's `math.gcd` (inference). No new dependency, and R-30's pin stays. Readable: one function with its reference (Knuth 4.5.2, Algorithm L). Risk: a gcd bug gives unreduced values, which the canonical-form check and the differential test catch.

**D2-2. Money as minor units** (amends A3 F-17 and BUILDER §2's `I64 | I128 | Big`).
- *Options:* (a) `I64 | I128 | Big`; (b) **`I64 | Big`**; (c) money as a `Num` with a unit.
- *Recommended:* **(b)**. (c) pays a gcd on every money add and loses the type wall that R-28 relies on.
- *Cost:* the least code of the three, and the same results.

**D2-3. Interning** (amends BUILDER §3's "no interner").
- *Options:* (a) `Box<str>` everywhere; (b) **one hand-written interner for all names and text keys**, with `Symbol(u32)` and output order by text (rustc's `stable_cmp`); (c) a crate (lasso, string-interner: both need hashbrown).
- *Recommended:* **(b)**.
- *Cost:* about 50 lines. Readability: names print through one `as_str`. Risk: an id order leaking into output. Guard it with R-47's review and T's property test that reorders files.

**D2-4. Ids and tables.**
- *Options:* (a) **an own `Table<I, T>` with `push`, `get` and `iter`, and no `Index` impl**; (b) typed-index-collections or index_vec; (c) la-arena or id-arena; (d) slotmap.
- *Recommended:* **(a)**. It matches BUILDER §3's `ItemId` table, generalised.
- *Cost:* about 40 lines, no dependency, and indexing becomes impossible rather than linted.

**D2-5. The collections policy** (refines BUILDER §7).
- *Options:*
  - (a) **BTreeMap/BTreeSet by default; sorted `Box<[T]>` for frozen tables; dense `Vec` for index-keyed memo and logs; IndexMap only where insertion order is the meaning; no small-vector crate.**
  - (b) (a) plus one sanctioned hash memo with a fixed in-repo hasher and an `Unord`-style API with no iteration (an R-36 exception).
- *Recommended:* **(a) now; (b) only if the first engine profile shows sparse memo lookups dominating** (a G1 question).
- *Cost:* (a) needs no new rule. (b) needs one counted exception and its own review.

**D2-6. Walk storage and overlays.**
- *Options:* (a) **`Vec<Rc<PlaceState>>` checkpoints with clone-on-write, layered pin and scenario contexts, a day column beside each log, parts as sorted label vectors**; (b) a persistent-map crate (rpds; imbl brings rand crates; im is unmaintained); (c) full copies at each checkpoint.
- *Recommended:* **(a)**.
- *Cost:* std only. Checkpointing is O(places), plus O(changed places) per day.

**D2-7. The memo's shape and scope.**
- *Options:* (a) one global memo for the run; (b) **one memo per evaluation context (seams J and F), dense per def where the key is a position, freed when the context ends**; (c) (b) plus an eviction budget.
- *Recommended:* **(b)**. Decide on (c) only after an engine run of B-07 (L:4).
- *Cost:* the context is already in the memo key (seam F), so this only decides who owns the cells.

## Unknowns until the engine runs

1. Whether `size_of::<Num>()` is 16 bytes. A compile settles it.
2. The share of *balanced* big gcds in E1. This decides how much D2-1's Lehmer actually buys. Engine counters settle it.
3. The real cost per Small operation and per dense or sparse memo probe against the per-node budget of 10–50 ns (shape.md point 7).
4. How many memo cells the engine makes once it skips empty days and shares walk prefixes. Every Q7 total depends on it.
5. B-07's and B-12's peak memory with per-context memos (L:4, L:5, L:14).
6. How often i64 intermediates overflow into i128 or Big *inside* an operation. shape.md sized results only.
7. Whether clippy's `indexing_slicing` flags `TiVec` or `IndexVec` indexing. Moot under D2-4 (a).

## Contradictions with phase 1, and spec observations

- **BUILDER §2:** "Write a Lehmer gcd … only if the benchmarks ask" against D2-1 (b). The new evidence is shape.md's E1 (5 049 bits on a household check) and the GMP thresholds.
- **A3 F-17 and BUILDER §2:** `Int = I64 | I128 | Big` for money, against D2-2 (b). PERFORMANCE §6 and BUILD-ORDER differ on it too (SO-20).
- **BUILDER §3:** "no interner", against D2-3. It doesn't conflict with R-47, which rustc's `stable_cmp` pattern honours.
- **RULEBOOK R-37** lists hashbrown as banned outright, while the scaffold's `deny-tally.toml` lets indexmap wrap it and BUILDER §7 allows IndexMap. The scaffold and BUILDER agree with each other; R-37's text should say "except under indexmap".
- **The R-28 ban on `Default`** rules out tinyvec for `Num`/`Money` payloads. That is not a conflict, a consequence.
- **Spec observations** (not fixed):
  - SO-24 (PERFORMANCE "16 bytes × 100 000 paths") holds for Small values under D2-1. Big values are variable-size.
  - LANGUAGE §7.1 R-13 leaves path statistics unbounded by the cap, so a quantile over 100 000 paths keeps every path's value (about 2.4 MB per figure at 24 B; inference). That is fine.
  - No new spec gap found.
