### Q1. How strict, well-regarded Rust projects stay readable

- **rust-analyzer's `architecture.md`** [S1]:
  - It has a "Bird's Eye View", a "Code Map" by directory, and bold **Architecture Invariant** notes that "often talk about things which are deliberately absent in the source code" ("parsing never fails").
  - It marks crates as **API Boundary**.
  - Its core crates "don't interact with the outside world and thus can't fail", the same rule as BUILDER §7.
- **matklad's post on ARCHITECTURE.md** [S2]: "Keep it short: every recurring contributor will have to read it". It holds only "things that are unlikely to frequently change", is "a map of a country, not an atlas", names modules but does "not directly link them (links go stale)", and is revisited "a couple of times a year".
- **rust-analyzer's style guide** [S3]:
  - "Avoid making a lot of code type parametric".
  - "do not hide control flow inside functions, push it to the caller".
  - "Express function preconditions in types".
  - "Avoid creating single-use helper functions".
  - "Use boring and long names for local variables"; no ad-hoc acronyms beyond a fixed few (`db`, `ctx`, `acc`).
  - "If writing a chain of combinators creates friction, replace them with control flow constructs: `for`, `if`, `match`."
- **rust-analyzer's tidy test** [S4]:
  - `TidyDocs` fails the build when a file's first line isn't a `//!` doc comment ("Missing docs strings"), with an exception list of test and data directories.
  - `TidyMarks` pairs marks in code with tests that check them.

  This is "every module explains itself", enforced.
- **typst** [S5] documents four phases, each mapped to crates, and states its principles plainly: "Typst ensures that all functions are pure", which makes memoisation safe. ENGINE's chapters (load, evaluate, walk, book, replay, paths, explain) give the same pipeline-shaped codemap (inference).
- **ruff** [S6][S7]: one file per rule, registered in one `codes.rs`. Each rule's doc has fixed sections ("What it does", "Why is this bad?").
- **cedar** [S8]:
  - Its Lean models "should be *human readable*", "serve as Cedar's *specification*", and are "an order of magnitude smaller than their Rust counterparts".
  - Differential random testing ("millions of inputs") plus property tests found 21 bugs. The Rust carries the "optimizations" and the diagnostics.
  - **Inference:** refcore is Tally's readable model, held to the engine byte for byte by gate 10. An owner who reads TypeScript follows Python far more easily than Rust.
- **TigerBeetle's TIGER_STYLE** (Zig) [S9]:
  - a hard 70-line function limit ("a sharp discontinuity between a function fitting on a screen, and having to scroll");
  - "Centralize control flow … keep all switch/if statements in the 'parent' function, and move non-branchy logic fragments to helper functions";
  - "push `if`s up and `for`s down"; "Keep leaf functions pure";
  - no recursion; "Put a limit on everything";
  - units last in names (`latency_ms_max`), no abbreviations;
  - comments say why; 100 columns.
- **Microsoft's Pragmatic Rust Guidelines** (2026.6, generated 2026-10-26) [S10]:
  - M-MODULE-DOCS ("Any public library module must have `//!` module documentation"), M-CANONICAL-DOCS, M-FIRST-DOC-SENTENCE ("approx. 15 words");
  - M-DOCUMENTED-MAGIC;
  - M-DI-HIERARCHY ("prefer concrete types over generics, and generics over `dyn Trait`");
  - M-SIMPLE-ABSTRACTIONS; M-MACRO-LAST-RESORT; M-HOTPATH; M-BALANCED-MODULES;
  - M-NO-META-DESIGN-DOCUMENTATION (document the end state, not the journey);
  - an AI section (M-DESIGN-FOR-AI).
  - It disagrees on names: M-SHORT-NAMES prefers abbreviations.
- **The pattern** (inference): a short map with invariants; one unit per file with a mandatory header, checked by script; closed sets as enums; few generics; control flow kept in one visible place; names from the domain. Only TigerBeetle caps length hard; the others cap nesting or review.
