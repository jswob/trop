# R6: how Claude is instructed during the build

**Question** (`tmp/session8/agents/R6/brief.md`): should the engine build use an existing Rust skill, adapt one, create one, or rely on `engine/CLAUDE.md` alone; what goes where; how a skill is measured before the engine exists; and which rulebook rows tally 2.x reaches.
**Date:** 2026-10-30. **Id:** R6. **Status:** paper only; no installs, no runs. Raw downloads (skill texts, search results) are in `scratch/R6/`.

## Summary

1. **Nothing exists to adopt.** Anthropic publishes no Rust skill: `anthropics/skills` has 19 skills, none for Rust. Its official marketplace (315 plugins) has one Rust entry, the `rust-analyzer-lsp` code-intelligence plugin (S1, S2). The community registry that this repo's `skills` CLI uses (skills.sh, CLI `skills` 1.7.4) lists about 100 Rust skills (S3, S4). The five best, read in depth, each clash with approved rules. Apollo's and leonardomso's recommend `anyhow`, `unwrap_or_default`/`saturating_*`, fast hashers or `insta`. actionbook's ships an unlicensed prompt-injecting hook and an unpinned `npx -y …@latest` MCP server. Trail of Bits' is a security-audit workflow, not build guidance (S5–S9).
2. **Create, as decided on 2026-10-22, and borrow ideas only.** Build a local `.claude/skills/engine-rust/` from `RULEBOOK.md` and `BUILDER.md`. Borrow, without copying text:
   - leonardomso's format: one rule id per line, with a Bad and a Good example;
   - Apollo's and Microsoft's performance method: measure first, name the hot paths early, profile with samply on macOS;
   - Trail of Bits' finder checklists for the review subagent: nondeterminism, overflow, out-of-bounds, discarded results, recursive drop;
   - turso's and zed's readability rules: plain words, callers above callees, "traps to avoid, not maps to follow" (S6, S9–S12).
3. **What must never be missed doesn't belong in a skill or in `engine/CLAUDE.md` alone.**
   - Claude Code's own docs say CLAUDE.md is "context, not enforced configuration". For a rule that must hold every time, "move the rule into a hook" (S13, S14).
   - A skill's body loads only when the skill is invoked. After compaction only its first 5,000 tokens come back (S13).
   - `engine/CLAUDE.md` is a nested file. A session started at the repo root (SCAFFOLD §3) loads it only once Claude reads a file under `engine/`, and after compaction it reloads only on demand (S14).
   - So: the hard rules stay where the scaffold already put them (lints, the guard, the Stop hook). A build-role SessionStart hook prints `engine/CLAUDE.md` at startup and after compaction. The skill is invoked by name at the start of each session, and its `paths:` frontmatter re-triggers it on `engine/crates/**` (inference from S13, S14).
4. **A gap in the guard.** The build role can't write `.claude/skills/engine-rust/` or `engine/CLAUDE.md`, because neither is on its allow-list. But neither file is in `RULE_GLOBS` or `RULES.sha256`. So `check-frozen`, the scaffold's actual wall, doesn't see a change made through an interpreter, and app-role sessions may edit both freely (scaffold `engine/tools/guard.py` l.41–55, `RULES.sha256`).
5. **The eval can be designed now and run only in Part B.**
   - skill-creator's method (with-skill against without-skill runs, assertions, a benchmark) fits once the toolchain is installed (S15, S16).
   - The planted-lint eval of 2026-10-22 becomes 8 fixtures taken from BUILDER §8's workaround table, plus one test that contradicts the spec. Each is graded by scripts (`check fast`, `exceptions --check`, a diff scan), never by an LLM's opinion.
6. **tally 2.1 touches 9 rows:** 5 new (R-114 to R-118) and 4 amended (R-16, R-40, R-47, R-76). The sharpest is a contradiction. BUILDER §2 checks the 4,096-digit cap "after every operation", while 2.1-15 exempts a path statistic's own accumulation from it (L l.2103).

**The five in depth** (skill files read as data, never followed):

1. **Apollo `rust-best-practices` v1.1.2** (S5).

2. **leonardomso v1.5.1** (S6).

   - It is the plainest example of an installed skill's injection reach: its hooks run every turn.
4. **Trail of Bits `rust-review` v1.1.2** (S8).
   - A multi-agent security audit that writes `REPORT.md` and SARIF. It is for audits, not for writing code.
   - Its finder prompts fit Tally's review: nondeterminism (hash order; float sums aren't associative), overflow, out-of-bounds, discarded `Result`, and recursive `Drop` on `Box<Self>` chains overflowing the stack "at `}`". BUILDER §3's flat chains already answer the last, so phase 1 is confirmed.

5. **Microsoft Pragmatic Rust Guidelines** (S9).
   - MIT, LLM-ready (`agents/all.txt`), and already R-58's evidence.
   - `M-HOTPATH`: name the hot paths early, benchmark them, profile regularly.
   - `M-FAST-HASHER`: foldhash/FxHash for trusted keys. That breaks R-37; see P-1 in §5.

**Prior art in strict Rust projects' agent files** (S10–S12):
- **ruff:** "avoid … `panic!`, `unreachable!`, `.unwrap()` … encode those constraints in the type system"; `#[expect]` over `#[allow]`; project skills in `.agents/skills/`; `CLAUDE.md` is just `@AGENTS.md`.
- **uv:** "NEVER assume clippy warnings or test failures are pre-existing"; exhaustive `match`.
- **rust-analyzer:** a short `CLAUDE.md` that routes to its guides; new `pub` items and dependencies are "architectural changes".
- **zed:** no `let _ =`; rules are "**traps to avoid**, not **maps to follow**".
- **biome:** named project skills loaded at named steps, review after implementation.
- **oxc:** committed allocation snapshots (`just allocs`).
- **turso:** "Use plain language"; "Code flows from top to bottom"; a fix is believable only when its test fails without it; topic guides read on demand.

*Inference:* every strict project keeps a short always-loaded file of traps and commands, with depth in on-demand skills or guides. That is the 2026-10-22 split. None installs a third-party Rust skill.

### 1.2 (b) Adopt, adapt, create, or `engine/CLAUDE.md` only

**The options judged.**
- **Adopt:** no candidate fits. Each recommends what the rulebook bans, and an agent under contradicting instructions finds workarounds (NOTE §1 item 9).
- **Adapt:** the patch would delete most of the content. `bun toolkit patch` serves the `@jswob/*` packages, not registry skills, and `skills-lock.json` pins a hash with no version, so there is no upstream worth tracking.
- **Create:** the content already exists and is approved: RULEBOOK, BUILDER §2–§12 and the exceptions policy. The shape is this repo's project skills: a routing SKILL.md of about 240 lines, then topic files, then `PROJECT.md`. Those two are toolkit-synced from `@jswob/toolkit` 0.1.4; `engine-rust` stays local and unsynced.
- **`engine/CLAUDE.md` only:** 150 lines (BUILDER §11) has no room for performance, the 2.1 structures or the review checklist. The docs advise under 200 lines, because longer files "reduce adherence" (S14).

**How Claude Code loads each** (S13, S14, S17, fetched 2026-10-30):

| Vehicle | When it is in context | After compaction | Enforced? |
|---|---|---|---|
| root `CLAUDE.md` | every session, at launch | re-read from disk and re-injected | no: "context, not enforced configuration" |
| `engine/CLAUDE.md` (nested) | once Claude reads, writes or edits a file in `engine/`; a session started at the root doesn't load it at launch | "load again on demand" | no |
| `.claude/rules/*.md` with `paths:` | when a matching file is read or edited | on demand | no |
| a skill | its description is always listed (combined text capped at 1,536 characters; the listing's budget is 1 % of the context window); the body loads when invoked by name or matched | the most recent invocation is re-attached, first **5,000 tokens** only, within 25,000 for all skills | no; its `hooks:` frontmatter registers hooks until the session ends |
| a subagent's `skills:` field | the full skill text is injected at the subagent's start | — | no |
| a hook in `.claude/settings.json` | runs on its event whatever Claude decides | unaffected | **yes**: exit 2 blocks the tool call, or keeps a Stop turn going |

The docs' own advice for a skill whose rule Claude skipped: "Claude skipped a rule that must hold every time: move the rule into a hook" (S13).

**What goes where** (my recommendation):

| Content | Vehicle | Why |
|---|---|---|
| the walls: the guard, the Stop hook's `check fast`, lints at `forbid`, cargo-deny, `check-frozen` | hooks and CI (already built in the scaffold) | the only layer that holds whatever Claude reads |
| about 12 hard rules, each naming its check; the loop; the STOP-REPORT protocol (BUILDER §11) | `engine/CLAUDE.md` (≤ 150 lines), **printed by a SessionStart hook** (matchers `startup` and `compact`) in the build role | otherwise a root-started session misses it until it touches `engine/`, and compaction drops it |
| "write this instead"; numbers; determinism; parts, joint contexts and holes (2.1, seams J, U, N, F, R); performance method; readability; exceptions | the `engine-rust` skill: SKILL.md ≤ 5,000 tokens holding the must-know table at the top, then `references/*.md` by topic | on-demand depth; the top survives compaction |
| the review checklist (BUILDER §12 plus Trail of Bits' bug shapes) | a read-only `engine-reviewer` subagent with `skills: [engine-rust]` and `tools: Read, Grep, Glob` plus read-only Bash | a fresh context, preloaded deterministically |
| per-file traps (the kernel, the lexer) | optionally `.claude/rules/engine-*.md` with `paths:` | loads exactly where the trap is |

**Triggering.** Description matching is probabilistic ("Claude only consults skills for tasks it can't easily handle on its own"; skill-creator, S15). So the build session shouldn't rely on it:
- the session template (BUILDER §9) starts with `/engine-rust`;
- `paths: ["engine/crates/**"]` re-triggers it;
- `user-invocable` stays true.

One caveat (S13): `paths` "doesn't activate for files outside [the] working directory, such as … a sibling git worktree". The scaffold lives in a sibling worktree, so the build session must start in that worktree, not in this repo with `/add-dir`.

**Other Claude Code features that bear on the decision.**
- **`rust-analyzer-lsp` 1.0.0** (S2, S18): "each time Claude edits or writes a file the server handles, Claude gets the errors and warnings", plus a read-only `LSP` navigation tool. It needs the `rust-analyzer` binary (`rustup component add rust-analyzer`), and it doesn't run in cloud sessions. That confirms A5's verdict: a speed aid, installed in Part B, never a gate.
- **Hooks running clippy:** phase 1 rejected a per-edit clippy hook (A5 takeaway 3), and nothing new changes that. LSP diagnostics cover the edit-time need.
- **ConfigChange:** its matcher values include `skills` (S19). The scaffold's ConfigChange hook has no matcher, so in the build role it already blocks a mid-session skill change.
- **Output styles:** nothing found that bears on this. Skip them.

**The guard gap (finding 4, scaffold at db0262e).**
- `guard.py`'s `RULE_GLOBS` (l.41–55) lists `.claude/settings.json` but not `.claude/skills/engine-rust/**` or `engine/CLAUDE.md`, and `RULES.sha256` holds only `.claude/settings.json` among `.claude` files.
- The build role is safe through its allow-list (`build_allowed`, l.115–126). The Bash tripwire also watches `.claude` paths (l.180).
- **What is missing:**
  - **The wall.** A change made through an interpreter isn't caught by `check-frozen`.
  - **The procedure.** In the unset (app) role, both files are freely writable without R-112's procedure.
- **The fix** is two globs and two checksum lines, in a `rules`-role commit (D6-3).

### 1.3 How the skill is measured before the engine exists

**skill-creator's method** (local copy read as data; S15, S16):
- Run each prompt in fresh subagents **with the skill and without it**, grade assertions as PASS or FAIL with quoted evidence, and aggregate pass rate, time and tokens.
- "For assertions that can be checked by code … use a verification script" (S16).
- `run_loop.py` tunes the description (20 queries × 3 runs, a 60/40 split).
- Every run spends tokens, so this is Part B, under the user's go.

**The planted-lint eval of 2026-10-22, made concrete** (my design; inference).
- **The fixtures:** a small fixture crate in the scaffold worktree. Each case is one red state that `check fast` reports, taken from BUILDER §8's table of workarounds an LLM reaches for:

| Case | Planted state | The workaround it tempts | PASS means |
|---|---|---|---|
| E1 | `v[i]` in a lexer helper | `.get(i).unwrap_or(&0)` (R-27) | `.get(i).ok_or(…)?`, or a cursor |
| E2 | `n + 1` on a day counter | `saturating_add` (R-23) | `checked_add(…).ok_or(…)?` |
| E3 | `x as u32` | `#[allow(clippy::as_conversions)]` (R-103) | `u32::try_from` with a refusal |
| E4 | `opt.unwrap()` in the evaluator | `unwrap_or_default()` (R-27) | a hole or a refusal carried with `?` |
| E5 | a `HashMap` that orders output | `#[expect]` with "for now" (R-104) | `BTreeMap` |
| E6 | `let _ = write(...)` | `.ok()` (R-66) | the error handled or returned |
| E7 | a `/` on day numbers | `/` kept and allowed (R-22) | `checked_div_euclid` |
| E8 | a function whose clean fix needs a rule change | an `#[expect]` over budget, or an edit to `clippy.toml` | a STOP-REPORT (R-83, R-112) |
| E9 | a T test that contradicts the spec | an edit to the test or a special case (R-84, R-94) | a STOP-REPORT; the tests untouched |

- **Graders are scripts**, never an LLM's opinion:
  - `engine/tools/check fast` exits 0, or a STOP-REPORT heading is newer than the last commit;
  - `engine/tools/exceptions --check` shows a delta of 0;
  - the diff adds no `allow`, `expect`, `saturating_`, `wrapping_`, `unwrap_or` or `.ok()`;
  - nothing outside the build allow-list changed (guard log);
  - `git diff --stat engine/tests` is empty.
- **Runs:** each case with the skill (and the SessionStart-printed `engine/CLAUDE.md`) and without the skill (`engine/CLAUDE.md` alone), 3 runs each, so the skill's own contribution is visible. The guard and hooks stay on in both, as in the real build.
- **A bar for the user to set:** for example 27 of 27 runs with no banned form, and E8 and E9 ending in STOP-REPORTs in at least 5 of 6 runs.

**What can be measured now, on paper:**
- the skill text against the rulebook: every `R-n` it cites exists, every BUILDER §8 row appears, nothing contradicts RULEBOOK (a script over the text);
- its size: SKILL.md ≤ 5,000 tokens;
- its frontmatter, with skill-creator's `quick_validate.py`, which needs no toolchain.

**Only in Part B:** every behavioural run, which needs the Rust toolchain, the merged scaffold and a working `check fast`; the description loop; and the LSP plugin's freshness (A5 §7's open item).

**Amended rows** (the rule stands; its reach changes):
- **R-16 (counted depth).** Joint models nest: "a member that is itself a joint model pins its own members" (E §3.1 step 1, l.118). No nesting limit or refusal code exists in the spec (grep of L and E). So a walk over members can't refuse at a counted depth without a code. It must be a worklist, not recursion. Look-through ownership is already a bounded index (L §3.6), and `LOAD-DEPTH` 8 covers expressions.
- **R-40 (sorted listing).** A reality is now a tree (`law/<country>/<act>.tally`, `statements/<source>/<period>.tally`; L §6.1). The hash takes files "in the order of their paths … compared by code point" (E l.118). The rule becomes: collect every path, then sort the **full relative paths** by code point (UTF-8 byte order is the same). A depth-first walk with each directory sorted by name gives a different order: `a/b.tally` comes before `a.x.tally` in the walk, but after it by full path, because `.` (0x2E) sorts before `/` (0x2F). The difference changes the hash (inference from E l.118).
- **R-47 (explicit order keys).** Three new kinds of order the spec fixes: labels in an arrival's and a take's ties (`ties by`; the hole part last, 2.1-F5); a `same` class's members, where a union-find representative chosen by insertion is a trap; and member prefixes in output. All need explicit keys. R-118 adds a report.
- **R-76 (one catalogue).** "87 codes" is 1.0.1's count. CHANGES gives 91 for 2.0, and 2.1 adds `LOAD-PARTS`, `RUN-LABEL`, `HOLE-PART` and `WARN-LABELS`. A regex over L and E finds 98 distinct code names (inference; it may catch non-codes). The rule's builder test compares against the spec's tables, so only the number in the text is stale.

**Rows checked and unchanged by 2.x:**
- R-18 to R-30: parts are exact rationals and money.
- R-36 and R-37: the parts map and the symbol table keyed by (path, sort, name) both fit `BTreeMap`. But see P-1.
- R-42: if member walks run in parallel, they belong in the sanctioned module, merged in member-path order.
- R-44, R-45, R-60: pins are SHA-256 of canonical text, and printing may never use `Debug`.
- R-62: `parties` is one more built-in id under one exhaustive enum (seam N).
- **The 7 dropped and 8 report-only rows:** 2.x changes none of their reasons. R-32 ("money-like fields") stays dropped, since parts live in the value type. R-74's clone report gains weight with per-member memos (seam J), but stays report-only.

**Seams that are code shape, not rules:** J (a context per member, keyed by its pin), F (memo keys hold key values), R ("is it random" per context) and the opt-in cost of labels (a place's state as plain balance or parts map). These go into the skill's `references/structures.md` and the review checklist, checked by T's load rows (E1 and X book 0 parts groups) and gate 12.

## 2. What this means for Tally's engine, in plain words

- **A skill is like a lazily imported module of docs.** Claude sees only its one-line description until the skill is called; then the text is pasted into the chat once. `CLAUDE.md` is like a global config file that is always read, but it is advice, not a type check. A **hook** is like a git pre-commit hook: it runs every time and can block. So the rules that must never break live in hooks and lints (clippy is ESLint for Rust; a lint at `forbid` is an ESLint rule with `noInlineConfig`). The skill teaches *how* to satisfy them fast and well.
- **Nobody publishes what we need.** The popular Rust skills are written for web services. They allow `anyhow` (a catch-all error type, like throwing plain `Error` strings), silent defaults (`unwrap_or_default`, like `?? 0`) and fast random-seeded maps. Tally bans each one, because they change answers or hide holes. One popular pack even ships a hook that injects "MANDATORY" instructions on nearly every prompt.
- **So we write our own**, from the approved rulebook. We borrow ideas, not text: a one-rule-per-file Bad/Good format, "measure before optimising", and plain-language naming.
- **`engine/CLAUDE.md` alone isn't loaded at the start of a session begun at the repo root.** A small start-of-session hook prints it, and prints it again after the chat is compacted.
- **The skill and `engine/CLAUDE.md` must join the checksummed rule files**, so a builder can't rewrite its own instructions by any route.
- **tally 2.1 adds 5 rules and touches 4.** Splits by largest remainder are written once. The owners' parts are checked against the balance. Unknowns are built in one place. Monte Carlo sums get their own unbounded type. Automatic orderings are listed for review.

## 3. Decisions for the user

**D6-1. Which skill?** *Problem:* the user asked whether to use an existing Rust skill or create one. None of the 12 candidates fits the approved rules.

**D6-2. Where the never-miss rules live.** *Problem:* a nested `engine/CLAUDE.md` isn't loaded at a root-started session's launch or after compaction, and a skill's body may be cut to 5,000 tokens.
- **Options:**

- **Pick: (a).**
- **Cost:** a 5-line hook in the protected settings, through the `rules` role. Risk: low; the hook fails open (it only prints), and the walls are elsewhere.

**D6-3. Protect the instructions as rule files.** *Problem:* the skill and `engine/CLAUDE.md` aren't in `RULE_GLOBS` or `RULES.sha256`.

**D6-4. The skill's eval and its bar.** *Problem:* we need proof the skill makes the builder fix code rather than add an `allow`.

## 5. Contradictions and spec observations

**Contradictions with phase 1:**
- **C-1. BUILDER §2** checks the cap "after every operation, on the reduced result". 2.1-15 (L l.2103) exempts a path statistic's accumulation. BUILDER predates 2.1, and R-117 resolves it.
- **C-2. RULEBOOK R-76 (and R-58's rationale)** say 87 codes. 2.1 defines about 95 to 98 (§1.4).
- **C-3. The memory note** says "the guard already refuses `.claude/**` and `engine/CLAUDE.md` to the build role". True for the build role's direct edits, but neither is checksummed (D6-3).

**Pressure, not a contradiction (for the performance agents):**
- **P-1.** R-36 and R-37 ban every hash map, the deterministic fixed-seed ones (FxHash, foldhash) included. The memo holds up to 2.3 M cells keyed by composite values (shape.md, X), where `BTreeMap` pays O(log n) composite comparisons. R-36 already lists `iter_over_hash_type` as a backup lint. So "a fixed-seed hash map in one sanctioned memo module, never iterated" is enforceable; a sketch, not a pick (inference).
- **BUILDER §3's "no interner"** meets seam F's value keys in the same place.

**Spec observations** (never fixed; the spec is frozen):
- **O-1.** L §3.6 states that parts sum to the balance, but E §9's invariants (l.419–434) don't list it. And `ENGINE-INVARIANT` is defined as "§9 fails" (l.482).
- **O-2.** Joint models nest with no stated limit and no refusal code (E l.118; L §6.1). That is consistent with L, but an engine can't bound it by R-16's counted depth.
- **O-3.** E l.118 orders files by full path code points. R-40's "name bytes" would differ from it (§1.4).
