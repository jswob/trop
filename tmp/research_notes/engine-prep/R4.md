# R4: measuring as a guarded habit

**Question:** how performance is measured from the first milestone, by checks an LLM builder can run and read but can't edit or game.
**Date:** 2026-10-30. **Agent:** R4, session 8 (engine prep, part A). Paper only: nothing was installed, built or benchmarked.
**Machine facts read on 2026-10-30** (`sw_vers`, `sysctl`, `pmset`, `gh repo view`): MacBook Pro 14" `Mac14,9`, Apple M2 Pro, **6 performance + 4 efficiency cores**, 32 GB, macOS 26.6.2, Command Line Tools only (no Xcode, so no `xctrace`), on battery when read. The repo `jswob/trop` is **private**, so `ubuntu-latest` gives 2 vCPU and 8 GB.

---

## Summary

1. **There are three instruments, and they never agree on noise. Only the two that count things should block a merge.**
   - *Counts the engine itself reports* (def cells, reads, walk days, legs: the units of `shape.md`) are exact and the same on every machine. They can block every PR. **(inference)**
   - *Instruction counts under Valgrind* (gungraun, the 2025 rename of iai-callgrind; 0.20.0, 2026-09-26) repeat to many digits and support absolute "hard limits" that exit with code 3. SQLite has run its performance work on cachegrind's counts for 17 years: "repeatable to 7 or more significant digits", while wall-clock time is "scarcely repeatable beyond one significant digit" (sqlite.org/cpu.html).
   - *Wall time and peak memory* are what DONE gate 12 judges. On GitHub-hosted runners the coefficient of variation (spread ÷ mean) is 2.66 %, which gives a 45 % false alarm rate at a 2 % gate (CodSpeed, 2025-07-30). Criterion's own FAQ says not to run it in CI. Wall time is therefore measured on the reference machine and judged at the milestone, never on a PR.
2. **Valgrind does not run on Apple Silicon** (valgrind.org, 3.28.0 of 2026-10-23: Darwin x86/amd64 only). So instruction-count gates live on Linux CI. The Mac has its own cheap proxy, which this note found: **`/usr/bin/time -l` on macOS 26 prints "instructions retired", "cycles elapsed" and "peak memory footprint"** for a whole process, with no sudo (local `time(1)`; `ri_instructions` and `ri_lifetime_max_phys_footprint` in the SDK's `sys/resource.h`).
3. **Strict projects report performance; they don't block on it.**
   - rustc-perf labels a regression after it lands and asks for a justification, using `instructions:u` (the triage log of 2021-07-06).
   - rust-analyzer's metrics job runs only on pushes to master and gates nothing.
   - ruff's CodSpeed jobs (simulation, memory, walltime) are not in its required checks.
   - Tally's blocking design (counts and hard limits on every PR, wall time at the milestone) is stricter than any of them. That is affordable only because counts don't flake. **(inference)**
4. **Profiling an LLM can read on this Mac:**
   - `samply` needs no sudo and no Xcode, but its last release (0.13.1) is from 2025-02, and it writes a Firefox Profiler JSON that needs a small summariser to become text.
   - `cargo flamegraph` (0.6.14) now needs `xctrace` on macOS, which needs full Xcode.
   - On Linux CI, gungraun's callgrind and DHAT modes print text tables and enforce limits.
5. **Release profile:** the scaffold's settings are what uv ships with (fat LTO, `codegen-units = 1`, `panic = "abort"`), plus `overflow-checks = true`.
   - Published costs of overflow checks are "a few percent" on integer-heavy code (Dan Luu). rustc's stage-1 test suite ran 23 m 19 s → 23 m 57 s (+2.7 %) with them on (rust#87784).
   - PGO (profile-guided optimisation) gives about 10 %, 0–20 % per workload, in oxc's measurement.
   - BOLT (a post-link optimiser) is ELF-only, so it can't run on the reference Mac.
   - Keep the profile. Measure the overflow-check cost once, at S. Leave PGO to M9 as a release-only extra that no budget may depend on.
6. **PERFORMANCE §8 for 2.1** gets four groups of rows: the spec's interactive targets, the six measured checks at 1×, the 18 load rows at full size, and a few micro rows. Each row has a size, a budget, a count budget, a memory budget and a place where it runs (§1 Q6, D4-6).
7. **The reference machine** is proposed as the user's M2 Pro, fingerprinted and on AC power. It runs through the self-hosted runner phase 1 already chose for fuzzing (R-92 b), with fuzzing and benchmarks never at once (D4-3). This settles NOTE SO-27.
8. **The 8 GB cap becomes two rows.** A hard ceiling of 8 GB peak footprint applies to any run. A budget of ≤ 4 GB applies to each load row, because 6 heavy jobs × 4 GB fit the 32 GB machine (32/6 = 5.3 GB each) **(inference)**.

### Q2. Noise, and what can block a merge without flaking

- **Shared runners.**
  - The coefficient of variation is 2.66 % on GitHub-hosted runners (Ubuntu 24.04, 4 vCPU). Getting false alarms down to 1 % needs a gate of about 7 %.
  - CodSpeed's bare-metal runners measured 0.56 %. That is a vendor's own study of 100 runs over ruff, uv, turbopack and reflex.
  - My arithmetic with their model, P = 2(1 − Φ(Δ/CV)), gives 45 % false alarms at 2 %, 6 % at 5 % and 0.85 % at 7 %.
  - Criterion's FAQ: "The virtualization used by Cloud-CI providers like Travis-CI and Github Actions introduces a great deal of noise".
- **Hardware counters on hosted runners.** GitHub's Linux VMs don't expose the performance counters, so `perf stat` reports "not supported" for instructions (actions/runner-images#4974). Instruction counts on hosted CI therefore come from Valgrind's simulated CPU.
- **Laptop noise (inference, from scheduler studies).**
  - macOS has no way to pin a thread to a core. The quality-of-service class (QoS: how urgent the OS treats a thread) chooses between P and E cores, and high-QoS work spills onto E cores once the P cores are busy (eclecticlight.co, 2024–2025).
  - With 6 P cores, a 6-worker run lands on E cores whenever anything else runs. Battery and Low Power Mode change power draw (Apple support 101613).
  - So the reference run needs AC power, an idle machine and a recorded state.
- **Where instruction counts mislead (inference, with sources noted):**
  - **memory-bound code.** A 2.3 M-cell memo (X in `shape.md`) is cache misses, not instructions. Gungraun's `Estimated Cycles` and CodSpeed's formula add L1 and last-level cache misses at 10–40 and 100+ cycles (CodSpeed docs).
  - **parallel code.** The counts sum the threads, so a 6-worker speed-up never shows.
  - **system calls and I/O.** CodSpeed's simulation excludes them; SQLite says I/O time "is not reflected".
  - **allocation.** It shows up as malloc's instructions, not as page faults.
  - Instruction counts are a proxy for a regression, not a measure of a budget in seconds.
- **What strict projects gate on:**
  - rustc reports `instructions:u` and labels regressions afterwards, asking authors to justify them (rustc-perf triage 2021-07-06; its significance test is an IQR fence over history, `comparison-analysis.md`).
  - rust-analyzer records build time and analysis-stats into a metrics repo after each push to master; no PR trigger.
  - ruff runs CodSpeed on PRs, but the benchmark jobs are absent from `required-checks-passed`.
  - SQLite measures with cachegrind on a fixed workload (`speedtest1.c`), but no merge gate is documented.
- **Determinism helps the counts.** R-36 already bans hash maps and randomly seeded hashers, the usual source of run-to-run jitter in instruction counts **(inference)**. Two things can still move them:
  - the toolchain, Valgrind and glibc versions, all pinned;
  - which CPU model the runner gets: CodSpeed saw GitHub assign different CPUs under a pinned image.
  - So hard limits carry a margin, and a toolchain bump re-baselines them as a `rules`-role change.

**Recipes the builder follows unaided:**
1. *Is it slower?* Run `engine/tools/perf row <id>`: one line per budget, with the counts.
2. *Where?* Run `engine/tools/perf profile <id>`. It runs samply on the Mac or perf on Linux, then the summariser, which prints the top 30 functions.
3. *Why more work?* Run `--stats` and diff the counts against the row's count budget and against refcore's counted run.

None of these steps needs sudo, a GUI or Xcode. Each tool is pinned and run only through `engine/tools/`, as R-82 requires **(inference: a design proposal)**.

### Q4. Release settings

- **The scaffold, read 2026-10-30:** `[profile.release] panic = "abort", overflow-checks = true, lto = "fat", codegen-units = 1, debug = "line-tables-only"`; `[profile.bench] overflow-checks = true`.
- **Cargo's rules:** `bench` inherits from `release`. Benches ignore `panic`, because the test harness needs unwinding. Per-package overrides "cannot specify the `panic`, `lto`, or `rpath` settings", so `overflow-checks` can be overridden per package (doc.rust-lang.org/cargo/reference/profiles.html).
  - So a criterion or gungraun bench measures the library with unwinding. Only the shipped binary aborts.
  - The cost of that difference is "slightly" in the perf book, unmeasured. End-to-end rows should time the release binary itself.
- **LTO and codegen units:**
  - The perf book: LTO "can improve runtime speed by 10-20% or more"; fat LTO "may improve performance … further (but not always)"; `codegen-units = 1` "may improve runtime speed".
  - Cargo's docs: thin LTO "takes substantially less time to run while still achieving performance gains similar to 'fat'".
  - uv ships fat LTO with `codegen-units = 1` and `panic = "abort"`. ruff ships fat LTO with 16 codegen units, and 1 for its parser and AST crates.
  - Both keep a `profiling` profile with `lto = false` and full debug info, because "compile times with `lto = fat` are completely untenable". They accept that "we are measuring something in benchmarks that we aren't shipping".
  - Tally's engine is one library plus num-bigint, so fat LTO's link time is likely seconds, not minutes **(inference; unmeasured)**.
- **`overflow-checks = true` (phase 1's open question, NOTE §3.2):**
  - Dan Luu (about 2015) measured bzip2 under clang's overflow sanitiser in trap mode at +1 % compression and 0 % decompression, and estimates "a few percent on typical integer-heavy workloads". Tight summing loops lost vectorisation and ran 4–6× slower.
  - rustc with overflow checks everywhere: the stage-1 test suite went 23 m 19 s → 23 m 57 s (+2.7 %); the worst instruction-count case was +23.8 % (`ctfe-stress-4`, rust#87784, 2021).
  - **For Tally the cost should be smaller (inference).** `arithmetic_side_effects` is denied (R-19), so the hot arithmetic already calls `checked_*` by hand, and the setting only adds checks to counted exceptions, std's generic code and dependencies.
  - The one place it could cost is **num-bigint's inner limb loops**, compiled with the same profile. If S measures a cost there, a per-package override `[profile.release.package.num-bigint] overflow-checks = false` is the narrow remedy, and it needs the user's approval because it changes R-8's reach.
- **PGO and BOLT:**
  - PGO is the compiler optimising from a recorded run, like a JIT's warm-up done ahead of time. rustc's book gives the `-Cprofile-generate` → `llvm-profdata merge` → `-Cprofile-use` steps; "All `rustc` flags have to be the same".
  - Gains: the perf book says "10% or more"; oxc measured about 10 % on its linter and 0–20 % on its parser (oxc#812, 2024), and its maintainers hesitated to add the release step.
  - cargo-pgo 0.3.0 (2026-01-25) wraps it. BOLT "operates on X86-64 and AArch64 ELF binaries" (LLVM's README), so it can't run on the Mac.
  - PGO is fed through `RUSTFLAGS`, which `check` clears (R-82). It would be its own release pipeline in `engine/tools/`.
  - The profile must not be trained on the gate's own inputs, or it overfits them **(inference)**.
- **Other settings:**
  - `target-cpu=native` makes a binary that may not run on CI's machines. Leave it off **(inference)**.
  - Allocators (mimalloc, jemalloc): the perf book reports "large improvements" in practice. That is a candidate for M9's measurements, not a decision now.

- **What runs where:**
  - **every PR, Linux CI (`check full`):**
    - T's runner also checks each vector's count budgets: deterministic, at 1 worker.
    - gungraun benches at 1× with **hard limits from `budgets.tsv`**, passed on the command line by `tools/perf`, so a bench file's own limits can't loosen them.
    - The soft % against the `engine` branch's last run is a report.
  - **nightly, the Mac runner:** every row's wall time and footprint, reported (BUILDER §9's "reported in the morning").
  - **milestone exit (BUILD-ORDER: "the budget rows it touches, at 1× size"):** the gate session runs `tools/perf milestone M<n>` on the reference machine. A miss blocks the tag.
- **How a miss is reported:** one line, `BUDGET E1/tx2_mtg_day wall(1w): median 1.42 s > 1.00 s (+42 %, 10 runs)` or `COUNT E1/tx2_mtg_day def_miss: 701 203 > 619 000`. A miss is red in `check`, so the Stop hook holds the turn (R-83). The builder's legal exit is a STOP-REPORT, BUILDER §9's form, with "a budget looks wrong" added as a trigger.
- **Closing the holes in the guard:**
  - `check.py`'s `CLEARED_PREFIXES` doesn't include `GUNGRAUN_` or `CRITERION_`, so an environment variable could loosen a limit. Add both.
  - Every benchmark checks its output hash against T's expected digest after timing, so a fast wrong answer fails.
  - R-93 (no test detection) and R-94 (special-casing scan) already cover code that spots a benchmark's inputs.
- **Count budgets as non-flaky proxies:** def-cell misses, read keys, walk days stepped, legs booked, parts groups, Big-tier results, and allocations (gungraun DHAT `totalblocks`, Linux). They are exact at 1 worker. With a shared memo, counts at 6 workers can vary when two workers compute one cell, so 6-worker rows check only the result hash **(inference)**.

### Q7. Memory as a measured budget

- **macOS:** `/usr/bin/time -l` prints "peak memory footprint", the watchdog's measure. Footprint counts compressed and swapped memory that resident size misses (WebKit bug 165533). Under pressure, resident size reads low exactly when a process is heaviest.
- **Linux:** max RSS from `getrusage` or `time -v`. Python's `ru_maxrss` is in bytes on macOS and in kB on Linux.
- **Hyperfine 2.0's `memory_peak_resident`** is resident size, not footprint **(inference from its name)**. Footprint rows use `time -l`.
- **Allocation counts:** gungraun's DHAT mode on Linux (`totalblocks`, `totalbytes`, peak), with hard limits. dhat-rs works on any platform but is "experimental" and unreleased since 2024-02.
- **The 8 GB cap becomes:**
  - (a) a ceiling on every run, which the perf runner enforces as `memcap.py` does;
  - (b) a ≤ 4 GB budget per load row;
  - (c) ≤ 512 MB per 1× check.
  - Hosted Linux has 8 GB in all, so rows near the cap run only on the Mac.

## 2. What this means for Tally's engine, in plain words

- **Three thermometers.**
  - The engine counts its own work, the way refcore's counted runs do. These counts are exact, like a test's assertion, so they can block a pull request without ever flaking.
  - Valgrind runs the engine on a simulated CPU and counts instructions. That is almost as exact, but it works only on Linux, and it misses memory stalls.
  - A stopwatch and a memory meter on the user's Mac measure what DONE actually promises. They are noisy, so they judge milestones, not pull requests.
- **Harnesses.** A benchmark harness is like a test runner that times things.
  - **criterion**, a crate (an npm package for Rust), times small functions.
  - **gungraun** counts instructions under Valgrind.
  - **hyperfine** or `/usr/bin/time` times the whole `tally` command, as `run.py` times refcore.
- **The builder can't move the goalposts.**
  - The budgets live in a checksummed file that T writes from the spec.
  - The runner that measures them, and the benchmarks themselves, belong to the lead. The guard refuses the builder's edits to them, as it does for tests (K-17, R-91).
  - Every benchmark also checks the answer, so "fast but wrong" fails.
  - A missed budget is a red line in `check`. The builder either makes the code faster or files a STOP-REPORT saying why the budget looks wrong; it never edits the budget.
- **The release build** is how Cargo compiles the shipped binary (Cargo is Rust's npm). The scaffold's settings are the fast ones popular Rust tools use:
  - LTO, link-time optimisation: the compiler optimises across the whole program at once, like a bundler's tree-shaking that also inlines;
  - one codegen unit: no splitting for parallel compiling, so slower to build and faster to run;
  - abort on panic. A panic is Rust's crash, like an uncaught exception; here it ends the process at once.
  - One safety setting stays on: integer overflow crashes instead of wrapping silently. Its cost is likely about 0–3 % for Tally, because the code already checks its arithmetic by hand. We measure it once, at the first milestone.
- **Profiling** means asking where the time goes. On the Mac, samply records without admin rights. A small script of the lead's turns its recording into a top-30 list the builder can read.

## 3. Decisions for the user

**D4-1. The measuring instruments.**
- *Problem:* phase 1 named only criterion (R-97), which measures wall time; wall time on shared CI is too noisy to judge, and criterion cannot fail a run.
- *Options:*
  - (a) criterion only, as scaffolded;
  - (b) three instruments: the engine's own counts through T's runner; gungraun (instructions, allocations) on Linux; wall time and footprint on the Mac through a lead-written `engine/tools/perf`, with criterion for micro rows;
  - (c) a service: CodSpeed or Bencher.
- *Pick:* **(b).**
- *Cost:*
  - build effort: the perf runner (about the size of `run.py`'s timing part), a samply summariser, gungraun benches, and a `counters` feature in the engine (D4-8);
  - readability: one-line results;
  - speed: none, since the counters are off in release;
  - risk: gungraun's runner version must match its library; Valgrind lives only in CI.
- (c) adds an account and sends data out for no gain over (b).

**D4-2. What blocks a merge, and where.**
- *Problem:* a gate that flakes trains the builder to ignore red.
- *Options:*
  - (a) report only, like rustc, rust-analyzer and ruff;
  - (b) counts and gungraun's hard limits block every PR on Linux CI; instruction drift against the `engine` branch is reported; wall time and footprint block only the milestone tag, run by the gate session on the reference machine;
  - (c) wall time blocks PRs on hosted CI.
- *Pick:* **(b).**
- *Cost:* hard limits need margins, and a re-baseline at each toolchain bump (a `rules`-role commit). (c) gives 45 % false alarms at a 2 % gate.

**D4-3. The reference machine** (DONE gate 12; NOTE SO-27).
- *Problem:* "the reference machine" is undefined.
- *Options:*
  - (a) the user's MacBook Pro M2 Pro (`Mac14,9`, 6P+4E, 32 GB, macOS 26), as a self-hosted runner;
  - (b) a GitHub-hosted runner: for this private repo, 2 vCPU and 8 GB on Linux, 3 M1 cores and 7 GB on macOS. It can't run 6 workers or 8 GB rows;
  - (c) rented bare metal (CodSpeed macro runners, $0.032/min).
- *Pick:* **(a)**, with these conditions:
  - on AC power, not in Low Power Mode, with no other heavy job and never during a fuzz run;
  - the pinned toolchain and the frozen release profile;
  - 1 worker unless the row says 6;
  - 2 warm-ups, then the median of 10 runs; a row passes when its median is within budget;
  - every report records `sysctl hw.model`, `sw_vers`, `rustc -V` and `pmset -g`.
  - A new Mac means a re-measure and the user's re-approval.
- *Cost:* the user's machine is busy during gate runs; laptop thermals stay an unknown.

**D4-4. Release profile, `overflow-checks`, PGO.**
- *Problem:* NOTE §3.2 left the cost of overflow checks and fat LTO open; PGO is unexamined.
- *Options:*
  - (a) keep the scaffold's profile, measure once at S;
  - (b) switch to thin LTO;
  - (c) add PGO now.
- *Pick:* **(a)**, with three additions:
  - At S the lead builds twice (overflow checks on and off) and reports the difference on the six checks. If num-bigint's loops cost over 3 %, the user decides on a per-package override for num-bigint only.
  - A `profiling` profile (release plus full debug info) for the builder's profiling only. Gates always measure `release`.
  - PGO only at M9, as a release-only step; every budget must be met without it. No BOLT (ELF only).
- *Cost:* small. PGO adds a training-run pipeline later.

**D4-5. Profiling recipes.**
- *Problem:* the builder needs "where does the time go" in text.
- *Options:*
  - (a) samply plus a lead-written summariser on the Mac; `perf report --stdio` and `callgrind_annotate` on Linux; the engine's counters first;
  - (b) install Xcode for Instruments and cargo-flamegraph;
  - (c) none: counts only.
- *Pick:* **(a).**
- *Cost:* samply has had no release since 2025-02, and macOS 26 is untested (an unknown). Xcode is many gigabytes and would need the user's go.

**D4-6. PERFORMANCE §8 for 2.1.**
- *Problem:* §8 is 1.0.1's and stale; gate 12 waits on it.
- *Options:*
  - (a) the four groups of §1 Q6: the interactive targets kept; the six checks ≤ 1 s and ≤ 512 MB; load rows that finish, non-MC ≤ 10 s, MC at N-2003's rate, ≤ 4 GB; micro rows ratcheted from S;
  - (b) the same groups with budgets set only after S measures (a floor-first approach);
  - (c) carry the old rows only.
- *Pick:* **(a)**, with every number marked "proposed" until the user approves it at G1, and refcore's figures as the floor column.
- *Cost:* a too-tight number later needs a logged spec change (DONE rule 1); a too-loose one hides a slow design.

**D4-7. Memory budgets.**
- *Problem:* the 8 GB cap is a watchdog, not a budget.
- *Options:*
  - (a) an 8 GB ceiling on every run, ≤ 4 GB per load row, ≤ 512 MB per 1× check, measured as peak footprint on the Mac and max RSS on Linux;
  - (b) the ceiling only.
- *Pick:* **(a).**
- *Cost:* footprint and RSS differ, so Mac rows are judged by footprint only.

**D4-8. How the engine exposes its counts.**
- *Problem:* count budgets need the engine to count. The spec defines no such output (spec observation below), and R-93 forbids test-only behaviour.
- *Options:*
  - (a) a cargo feature `counters`, off in release (like R-51's fault injection), that prints `shape.md`'s units on stderr behind `--stats`;
  - (b) counters always compiled, printed on a flag;
  - (c) no counters; instruction counts only.
- *Pick:* **(a).**
- *Cost:* the counted build differs from the timed build. That is fine, because counts are deterministic and outputs must stay byte-identical (gate 12).

## 4. Unknowns until the engine runs

- The cost of overflow checks, in particular inside num-bigint, and the gap between fat and thin LTO on Tally's own code.
- Fat LTO's build time, which sets how slow a bench iteration is.
- How stable gungraun's counts are across the CPU models GitHub hands out, which sets the hard-limit margins.
- Valgrind's slowdown on the six checks. If an engine run takes 1 s, callgrind may take tens of seconds or more **(inference)**, which bounds how many rows run on every PR.
- Whether `ri_instructions` counts kernel instructions, and whether it sums all threads (it is per process).
- Whether samply records correctly on macOS 26.6.
- The engine's nanoseconds per node, and its memo cell size against the 512 MB and 4 GB budgets.
- Whether count budgets hold at 6 workers.
- Laptop thermals over a 10-run median.
- The 10× generator's definition (N-2002), which is T's.

## 5. Contradictions with phase 1 and the spec; spec observations

1. **R-97 and the scaffold's `bench` job measure on `ubuntu-latest`**, keeping criterion reports as gate 12's evidence. DONE gate 12 judges "on the reference machine", and criterion's FAQ advises against CI timing. Hosted runs can't be that machine (2 vCPU and 8 GB for this private repo). Wall-time evidence should come from the Mac runner, with Linux kept for counts.
2. **DONE gate 12's evidence column says "criterion reports".** Most §8 rows are end-to-end runs (a reality plus asks), which a CLI timer measures; criterion fits only the micro rows. *Spec observation:* the evidence would read "the perf runner's reports and criterion's", a DONE change for the user to log.
3. **DONE gate 12 cites `tmp/design2/benchmarks.md`.** Since 4.5f the list is `engine/tests/load/benchmarks.md`. *Spec observation.*
4. **`check.py` clears `CARGO_PROFILE_*` and similar but not `GUNGRAUN_*` or `CRITERION_*`** (R-82's intent). A gap to close when the benches are written.
5. **BUILDER §9 names no budget step at milestone end**, though BUILD-ORDER's summary requires "the budget rows it touches, at 1× size". *Suggestion:* add the gate session's `tools/perf milestone` run there.
6. **The `bench` profile ignores `panic = "abort"`** (Cargo's docs), so library benches don't measure the shipped panic strategy. That is acceptable, since end-to-end rows time the release binary. It is worth one line in SCAFFOLD.md.
7. *Spec observation:* LANGUAGE and ENGINE define no counters or stats output. D4-8 keeps them a build-side instrument (a feature off in release), so the spec needn't change. If the user wants `--stats` in the shipped CLI, that is a spec addition under DONE rule 1.
8. *Spec observation:* PERFORMANCE §8's interactive rows are sized by "the prototype's instances", a tally 1 notion. Their 2.1 sizes need T's generator definition before the rows can be judged.
9. **The machine has 4 efficiency cores beside its 6 performance cores.** The memory note "6 performance cores" is right. A 6-worker row is clean only on an otherwise idle machine.
