# R5: readable Rust that its owner can follow

**Question:** how the engine's code stays readable for an owner who can't read Rust, while an LLM writes it under phase 1's strict rules, with performance as a core aim. **Date:** 2026-10-30. **Agent:** R5, session 8 (engine prep, part A). **Paper only.** Nothing was built or run. All web sources were fetched 2026-10-30.

## Summary

1. **The owner reads the map, the trace and the reports, not the Rust.**
   - Strict projects explain themselves in two places: a short `ARCHITECTURE.md` (a codemap plus invariants, rust-analyzer [S1][S2]), and a `//!` header that every file must start with, enforced by rust-analyzer's tidy test [S4].
   - Tally adds what Cedar has, a readable twin: refcore. Cedar's Lean model is "an order of magnitude smaller" than its Rust and is held to it by differential tests [S8].
   - Each engine module names its refcore twin and its spec sections.
2. **A small Rust subset reads better at no loss of speed.**
   - Closed `enum`s with exhaustive `match`, never trait objects (`dyn`), which prevent inlining [S13].
   - No own generics, `impl Trait` arguments, library macros, or new traits without a counted reason.
   - Short iterator chains: loops and iterators benchmark alike, 19.62 against 19.23 ms [S16].
   - ast-grep matches every one of these constructs [S11].
3. **Strictness is not where speed goes.**
   - Readyset removed all bounds checks from a production Rust engine and called the cost "negligible" [S31].
   - `shape.md` puts the order of magnitude in structure: empty days, shared walks, the memo, the read index.
   - That code goes in fenced modules, each with a benchmark, a plain twin and an explanation (inference).
4. **K-21 changes in part.**
   - Clippy's own complexity score adds **1 for a whole `match`, whatever its arm count** [S18]. A long dispatch `match` isn't the problem; nesting is.
   - `excessive_nesting` becomes an **error at 5**, as A1 proposed. Length stays a report at 100 lines; the studies conflict [S23][S24].
   - `too_many_arguments` (7) and `type_complexity` (250) are **already errors**, through the scaffold's denied `complexity` group.
5. **The spec trace is cheap and checkable.**
   - The spec is frozen, so `L §5.11` and `L l.1451` never go stale.
   - A ~150-line script fails on cited sections that don't exist, requires citations in the kernel (R-75 becomes an error there), and prints the reverse map: section → code → refcore → tests.
   - refcore already cites 69 sections this way. Prior art: the Rust Reference's `//@ reference:` test headers [S27]; rustc tidy [S22].
6. **Readable strictness:**
   - Domain newtypes with checked methods (`DayNo::next()?`), which cost nothing ("elided at compile time" [S33]).
   - Named helpers in one kernel module.
   - Iteration instead of index arithmetic.
   - No macros or operator-like extension traits, which hide checks from clippy and mutation testing.
7. **Decisions D5-1 to D5-7:** layout and names; the subset; size limits; the trace; the owner's audit kit; performance fences; readable strictness. Each is made of rows the owner can approve one by one, like the rulebook's.

## Findings

### Q1. How strict, well-regarded Rust projects stay readable

- **rust-analyzer's `architecture.md`** [S1]:
  - It has a "Bird's Eye View", a "Code Map" by directory, and bold **Architecture Invariant** notes that "often talk about things which are deliberately absent in the source code" ("parsing never fails").
  - It marks crates as **API Boundary**.
  - Its core crates "don't interact with the outside world and thus can't fail", the same rule as BUILDER §7.
- **matklad's post on ARCHITECTURE.md** [S2]: "Keep it short: every recurring contributor will have to read it". It holds only "things that are unlikely to frequently change", is "a map of a country, not an atlas", names modules but does "not directly link them (links go stale)", and is revisited "a couple of times a year".
- **rust-analyzer's style guide** [S3]:
  - "Avoid making a lot of code type parametric".
  - "do not hide control flow inside functions, push it to the caller".
  - "Express function preconditions in types".
  - "Avoid creating single-use helper functions".
  - "Use boring and long names for local variables"; no ad-hoc acronyms beyond a fixed few (`db`, `ctx`, `acc`).
  - "If writing a chain of combinators creates friction, replace them with control flow constructs: `for`, `if`, `match`."
- **rust-analyzer's tidy test** [S4]:
  - `TidyDocs` fails the build when a file's first line isn't a `//!` doc comment ("Missing docs strings"), with an exception list of test and data directories.
  - `TidyMarks` pairs marks in code with tests that check them.

  This is "every module explains itself", enforced.
- **typst** [S5] documents four phases, each mapped to crates, and states its principles plainly: "Typst ensures that all functions are pure", which makes memoisation safe. ENGINE's chapters (load, evaluate, walk, book, replay, paths, explain) give the same pipeline-shaped codemap (inference).
- **ruff** [S6][S7]: one file per rule, registered in one `codes.rs`. Each rule's doc has fixed sections ("What it does", "Why is this bad?").
- **cedar** [S8]:
  - Its Lean models "should be *human readable*", "serve as Cedar's *specification*", and are "an order of magnitude smaller than their Rust counterparts".
  - Differential random testing ("millions of inputs") plus property tests found 21 bugs. The Rust carries the "optimizations" and the diagnostics.
  - **Inference:** refcore is Tally's readable model, held to the engine byte for byte by gate 10. An owner who reads TypeScript follows Python far more easily than Rust.
- **TigerBeetle's TIGER_STYLE** (Zig) [S9]:
  - a hard 70-line function limit ("a sharp discontinuity between a function fitting on a screen, and having to scroll");
  - "Centralize control flow … keep all switch/if statements in the 'parent' function, and move non-branchy logic fragments to helper functions";
  - "push `if`s up and `for`s down"; "Keep leaf functions pure";
  - no recursion; "Put a limit on everything";
  - units last in names (`latency_ms_max`), no abbreviations;
  - comments say why; 100 columns.
- **Microsoft's Pragmatic Rust Guidelines** (2026.6, generated 2026-10-26) [S10]:
  - M-MODULE-DOCS ("Any public library module must have `//!` module documentation"), M-CANONICAL-DOCS, M-FIRST-DOC-SENTENCE ("approx. 15 words");
  - M-DOCUMENTED-MAGIC;
  - M-DI-HIERARCHY ("prefer concrete types over generics, and generics over `dyn Trait`");
  - M-SIMPLE-ABSTRACTIONS; M-MACRO-LAST-RESORT; M-HOTPATH; M-BALANCED-MODULES;
  - M-NO-META-DESIGN-DOCUMENTATION (document the end state, not the journey);
  - an AI section (M-DESIGN-FOR-AI).
  - It disagrees on names: M-SHORT-NAMES prefers abbreviations.
- **The pattern** (inference): a short map with invariants; one unit per file with a mandatory header, checked by script; closed sets as enums; few generics; control flow kept in one visible place; names from the domain. Only TigerBeetle caps length hard; the others cap nesting or review.

### Q2. A simple Rust subset for LLM-written code

ast-grep (pinned at 0.51.0 in the scaffold's CI, still the latest today [S12]) matches tree-sitter-rust node kinds. `dynamic_type`, `type_parameters`, `trait_item`, `lifetime`, `closure_expression` and `macro_definition` all exist [S11].

| Limit | Saves the reader | Enforced by | Speed cost |
|---|---|---|---|
| **No `dyn Trait`**; a closed set is an `enum` plus exhaustive `match` (R-62) | every case listed in one place | ast-grep `dynamic_type`, error. An ast-grep rule has no counted exception (R-109 bans `ast-grep-ignore`), so a real need is a STOP-REPORT or a file the lead sanctions (R-108's way) | **a gain**: dynamic dispatch "prevents the compiler from choosing to inline" [S13]. enum_dispatch 0.3.13 reports up to 10× over `dyn` on its stated benchmark (1 024 objects, `black_box`) [S14] |
| **No own type parameters** (`fn f<T>`, `impl<T>`); std containers are fine | one concrete type per name | ast-grep `type_parameters`, report and review | none at run time (monomorphised, "static dispatch" [S13]); faster compiles [S3] |
| **No `impl Trait` arguments** | one signature form | clippy `impl_trait_in_params` (restriction) [S20] | none |
| **No new trait without two implementations** (BUILDER §11) | no abstraction ahead of need | ast-grep `trait_item` report, review | none |
| **Explicit lifetimes only on short-lived views** (the cursor, a borrowed slice); long-lived links are ids into tables (BUILDER §3) | the hardest Rust idea stays in a few files | ast-grep report on structs with a `lifetime`; the pedantic lifetime lints | a table lookup per id; clones cost more and are counted by R-74 (inference) |
| **No `macro_rules!` in the library** outside the lead's list; no own proc macros | no hand-expanding; clippy and cargo-mutants see the code (R-13, R-73) | ast-grep `macro_definition` (R-73's rule) | none |
| **Chains of at most about 4 steps; one-expression closures, none nested** | a `for` reads line by line | review; ast-grep report on nested `closure_expression` | none: loop 19.62 ms, iterator 19.23 ms [S16] |

**Why this pays (inference):**
- Every set of cases (node kinds, value kinds, codes, distributions) is fixed by the frozen spec. So `enum` plus `match` is both the fastest and the most readable shape.
- Generics, traits and `dyn` serve unknown future callers, and the engine has none.
- **Cost:** a little duplication, which rust-analyzer and TigerBeetle accept.

### Q3. Enforceable size and complexity limits

**What the lints measure** (clippy master source and book, today):
- **`too_many_lines`** (pedantic, default 100): counts lines with code only, and skips closures [S17][S15]. The scaffold allows it in the strict passes (R-67) and reports it at **60** in `tools/advisory.py`. A5 SC-6 said 100.
- **`cognitive_complexity`** (restriction, default 25): 1, plus 1 per `if`, **plus 1 per multi-arm `match`, whatever its arm count**, plus 1 per guard, minus returns. Clippy's own docs: "The true Cognitive Complexity of a method is not something we can calculate using modern technology" [S18].
- **`excessive_nesting`** (complexity, default 0 = off) [S19]:
  - A syntax-level pass. Every `{}` block, `impl` and inline `mod` adds a level, so a method body starts at 2.
  - It skips macros.
  - The scaffold denies the whole `complexity` group (`engine/Cargo.toml`), so **a threshold in `clippy.toml` makes it an error at once**. The advisory pass uses 4.
- **`too_many_arguments`** (complexity, 7) and **`type_complexity`** (complexity, 250) [S20][S21]: **already errors** in the scaffold.
- **File size:** clippy has no limit [S15]. rustc's tidy caps files at 3 000 lines and lines at 100 columns [S22].

**Evidence on length conflicts:**
- 785 000 Java methods: "keep their Java methods under 24 lines" [S23].
- A re-analysis calls the optimum "a sloppy analysis in one paper" [S24].
- Ousterhout warns against "teeny-tiny methods" and "arbitrary numerical limits" [S25].
- GitClear, via a secondary report, measured an eightfold rise in duplicated blocks in 2024 [S26]: the LLM-era risk is duplication, not length.

**Should K-21 change? Partly** (inference):
- Phase 1's reason, long dispatch `match`es, concerns length, which stays a report. Nesting is what a reader trips on.
- TIGER_STYLE's "centralize control flow" (branches stay in the parent, straight-line work goes to named helpers) meets a nesting cap without mechanical splitting.
- **Proposal:**
  - `excessive_nesting` as an **error at 5**: `impl` → body → loop → arm → `if` passes, and one level deeper fails (A1's figure).
  - `cognitive_complexity` reported at 25.
  - `too_many_lines` reported at 100.
  - Each arm of a dispatch `match` is a call or one expression (review; an ast-grep report flags arms over about 5 lines).
  - Files over 1 000 code lines are reported.

### Q4. A trace from code to spec that a script can check

**Prior art:**
- **The Rust Reference** links compiler tests to its rules with a test header, `//@ reference: x.y.z`, repeated when a file covers several rules. It says "Always annotate with the most specific rule name available", and an appendix "tracks how the rules are currently linked". The bar is "Complete coverage is the goal but is not yet expected", and editors are responsible for "ensuring every rule has a test associated with it" [S27].
- **Ferrocene's** language spec (now the Rust project's FLS) reuses its paragraph ids in tests for qualification. Assessors ask whether each part of the spec is tested [S28].
- **rustc's tidy** checks that "error codes are properly documented and tested" [S22]. Phase 1 already copies this for the 87 codes (R-76).
- **rust-analyzer's `TidyMarks`** pairs a mark in code with a test that checks it [S4]: a code-to-test trace.
- **Cedar** ties code to its spec by behaviour (differential tests), not by citations [S8].

**What Tally has already** (this session's grep):
- refcore cites spec sections as `L §n.m` in its sources: 69 distinct sections across its 30 files. Its tests are named by section (`L5_14_move.test`; HANDOVER § Layout).
- The scaffold's `advisory.py` already has a citation pattern (`[A-Z][A-Z-]*(\.md)? §n(.m)*`) and lists uncited kernel functions (R-75, report). It does **not** check that a cited section exists.
- BUILDER already cites lines (`LANGUAGE l.1451`).

**Why a strict trace is cheap here (inference):**
- The spec is frozen and checksummed (`SHA256SUMS`, DONE rule 1), so section numbers *and line numbers* never move.
- The headings are regular: LANGUAGE has 66 numbered `##`/`###` headings and ENGINE has 21.
- **The script:**
  1. Parse the headings of `engine/spec/*.md` into a set, `L §5.11` and so on.
  2. Scan the doc comments for `L §…`, `E §…`, `O §…` and `l.N`.
  3. Fail on an unknown section or a line past the end.
  4. Fail on a kernel function (the R-85 list) with no citation.
  5. Write the reverse map: section → code items → refcore files that cite it → T tests by name.
  6. Report the sections no code cites.
- It is about 150 lines of Python, the size of `advisory.py`. It needs no Rust parsing beyond what `check_rules.lex` already does.

### Q5. How a non-Rust owner audits

**The sources** suggest an owner reads three things:
- the map (`ARCHITECTURE.md`, short, revisited "a couple of times a year") [S2];
- the module headers, enforced by a script [S4], in a fixed shape like ruff's rule docs [S7] or Microsoft's canonical sections [S10];
- the reports a machine can make.

What Tally adds (inference):
- **The refcore twin.** Each Rust module's `//!` names the refcore file and functions it matches. The owner can then read the twin, in a language near TypeScript, and the spec section, rather than the Rust.
- **One milestone page**, generated by script from what the build already produces:
  - new and changed modules with their one-sentence purpose;
  - spec sections newly covered, and those still uncovered;
  - the exception lock's new rows with their reasons (R-113);
  - the nesting, length and clone report deltas;
  - the benchmark deltas against gate 12's rows;
  - new performance fences.
- BUILDER §12's checklist covers correctness. A short **readability section** is added for the fresh reviewer, so the owner reads the reviewer's verdict, not the diff.

### Q6. Where performance code may be less readable, and how it is fenced

**Prior art:**
- The perf book: measure after each inlining change, "because the effects can be unpredictable". Split a function into a hot `#[inline(always)]` part and a cold part only where profiling shows it [S29].
- Bounds checks cost "less often than you might expect"; iterate rather than index [S30].
- Readyset measured removing all bounds checks from its Rust SQL cache and judged the cost "negligible" [S31].
- M-HOTPATH: identify the hot path early, benchmark it with criterion or divan, profile regularly [S10].
- TIGER_STYLE: back-of-the-envelope sketches over the four resources [S9].
- matklad: "push `for`s down" (batching), whose "primary benefit here is performance" [S32].
- Cedar keeps the optimisations in the Rust and the clarity in the model [S8].

**Where the fences fall, from `shape.md` (inference):**
- the day walk's skipping of empty days and its shared prefixes (checkpoints; seam J);
- the memo and its key (seam F) and the cell size at 2.3 M cells;
- the read index by (input, keys);
- `Num`'s small and big tiers, already a twin pair with a property test in BUILDER §10;
- the thread module.

Everything else stays plain. Each fence carries:
- the plain form it replaces, kept where cheap as the test oracle;
- a named benchmark that proves the gain;
- a property or differential test that fast equals plain;
- a `PERF:` section in its `//!` saying all three in plain words.

A script checks that each `PERF:` names a benchmark and a test that exist. `#[inline(always)]` and `#[cold]` are reported outside fences.

### Q7. How the rulebook's strictness stays readable

**Newtypes** (a struct wrapping one number to give it a meaning, like a branded type in TypeScript):
- The Rust book: "no runtime performance penalty … the wrapper type is elided at compile time" [S33].
- `DayNo::next(self) -> Result<DayNo, Refusal>` names the domain step, and the check sits inside, written once. `Depth::deeper` in BUILDER §3 is exactly this.
- **Cost:** a type per domain integer: days, offsets, counts, depths.

**Named helper functions** in one small module, for example `fn inc(n: usize) -> Result<usize, Internal>`:
- The `?` at each call site keeps "this can refuse" visible.
- The module sits in the mutation kernel (gate 8), so its checks are tested.

**Iteration instead of index arithmetic** (`enumerate`, `zip`, `windows`, slice patterns):
- It removes most `i + 1` and `x[i]` at the source [S30]. A2's cursor shows the lexer done this way.

**Extension traits** (adding methods to built-in `u32`, like monkey-patching `Number.prototype`, but type-checked):
- They read like std, so a reader can't tell a project method from a built-in.
- A name like `plus` is an operator in disguise, the door R-20 closes.
- Recommendation: not used for arithmetic.

**Macros** (`add!(a, b)`): ruled out.
- They hide the `?` and the check, clippy partly can't see inside them (R-13), and cargo-mutants doesn't mutate them (R-73).
- M-MACRO-LAST-RESORT [S10].

## What this means for Tally's engine (plain words)

- **You won't read Rust, and you shouldn't have to.** Each file starts with a short plain-English header: what it does, which spec sections it implements, which refcore file is its Python twin, and what it deliberately doesn't do. A script fails the build if a file has no header, or if a header cites a spec section that doesn't exist.
- **One map, `engine/ARCHITECTURE.md`, under about 200 lines.** It follows the run: load → evaluate → walk → book → replay → explain → output. It lists each module's job and its invariants ("the library never reads the clock"). You read it once at S and again when it changes.
- **The code uses a small dialect of Rust.**
  - A *trait* is an interface. A *`dyn` trait object* is a value whose class is only known at run time, like calling through an interface in TypeScript. *Generics* are type parameters, like `<T>` in TypeScript.
  - The engine uses almost none of these. A fixed set of cases is an `enum` (a tagged union) with a `match` (a `switch` the compiler checks for completeness). That shape is both the easiest to read and the fastest, because the compiler can inline it.
- **Size rules:** deep nesting fails the build. Long functions are only reported, because a flat `switch` over 40 node kinds is long but easy. The two size checks already on (at most 7 arguments, no monster types) stay.
- **Speed lives in a few fenced places:** the day walk, the memo, the read index, the number fast path, the threads. Each fence has a benchmark that proves it pays and a test that it matches the plain version. Elsewhere, plain code is as fast as clever code, since bounds and overflow checks cost next to nothing in measured engines.
- **The strict rules stay readable** through small named types and helpers. A `DayNo` type whose `next()` can refuse reads like the spec. No macros and no tricks that hide a check.

## Decisions for the user

Each rule is given with its enforcement and its cost, so it can be approved row by row like the rulebook. Costs: **E**ffort to build, **R**eadability, **S**peed, **K** (risk).

**D5-1. Layout, map and names.**
*Problem:* the owner needs to find "where the engine does X" without reading Rust, and an LLM drifts without a fixed map.
*Options:*
- (a) no map, review only;
- (b) **`ARCHITECTURE.md` plus a mandatory `//!` header per file, checked by script, plus spec words as names**;
- (c) (b) plus a generated per-module guide in plain English.

*Pick (b).* The rows:
- **RD-1:** `engine/ARCHITECTURE.md`, at most about 200 lines: bird's-eye view, codemap by pipeline stage, invariants (including what is absent), boundaries (library against CLI, the sanctioned I/O and thread files). It names modules, never links them [S2]. Written at S, read by the owner, updated only at milestones. *Enforced by:* review at the milestone gate.
- **RD-2:** every `.rs` file starts with `//!`, giving the purpose in one sentence of about 15 words, then `Spec:`, `Twin:` (the refcore file) and `Invariants:` lines. *Enforced by:* a script error, modelled on rust-analyzer's TidyDocs [S4].
- **RD-3:** one directory per pipeline stage, mirroring refcore's Layout table where it fits; `foo.rs`, not `foo/mod.rs` (the scaffold already denies `mod_module_files`). *Enforced by:* review.
- **RD-4:** names use the spec's words (`law_date`, `cut`, `day_walk`, `read_rule`); units go last (`days_max`) [S9]; no abbreviations beyond a short list (`id`, `ctx`) [S3]. *Enforced by:* review. Pedantic's `many_single_char_names` is already on.

*Cost:* E low (one script, about 40 lines); R high gain; S none; K low.

**D5-2. The Rust subset.**
*Problem:* an LLM reaches for traits, generics and macros that the owner and the reviewer can't follow, and that add nothing to a closed interpreter.
*Options:*
- (a) review only;
- (b) **rows RS-1 to RS-7 below, tool-enforced where a tool exists**;
- (c) (b) with generics and macros banned outright, with no exception.

*Pick (b).* The rows:
- **RS-1:** no `dyn`. *Enforced by:* ast-grep, error. A real need is a STOP-REPORT, or a file the lead sanctions as R-108 does, because ast-grep rules take no `#[expect]` (R-109).
- **RS-2:** no own type parameters. *Enforced by:* an ast-grep report, then review.
- **RS-3:** no `impl Trait` arguments (clippy `impl_trait_in_params`, error).
- **RS-4:** no new trait without two implementations (ast-grep `trait_item` report, review).
- **RS-5:** explicit lifetimes only on short-lived views (ast-grep report on structs with lifetimes).
- **RS-6:** no `macro_rules!` in the library outside the lead's list. This raises R-73 from report to an ast-grep error outside the listed files, which is a rules change through R-112.
- **RS-7:** iterator chains of about 4 steps at most, single-expression closures, no nested closures (review, plus an ast-grep report).

*Cost:* E low (5 ast-grep rules with selftest cases, R-78); R high; S neutral or a gain (no `dyn`; iterators equal loops [S13][S16]); K: some duplicated code where a generic would share. Duplication is reported, never banned.

**D5-3. Size and complexity limits (revisits K-21).**
*Problem:* phase 1 made length and nesting advisory. The evidence says nesting, not length, is what hurts, and a flat `match` is cheap even by clippy's measure.
*Options:*
- (a) keep K-21 as is;
- (b) **nesting becomes an error at 5; length and cognitive complexity stay reports at clippy's defaults (100, 25); a dispatch-arm convention; a file-size report at 1 000 code lines**;
- (c) TigerBeetle's hard 70-line limit.

*Pick (b).* Also record in the rulebook that `too_many_arguments` (7) and `type_complexity` (250) are already errors through the complexity group, and fix the advisory thresholds (60/20/4) to match the rulebook.
*Cost:* E low (one `clippy.toml` line through R-112, plus a selftest case); R gain; S none; K: some refactors in the lexer and the walk. The approved exception budgets are 0 for the library and the parser (RULEBOOK §7.1), so the threshold must be one the code can meet without exceptions; it is re-judged at S (unknown 1). Option (c) risks the mechanical splitting that Ousterhout and A5 warn about [S25].

**D5-4. The spec trace.**
*Problem:* R-75 only lists uncited kernel functions. Nothing checks that a citation is real, and nothing shows which sections have no code.
*Options:*
- (a) keep R-75 as a report;
- (b) **a `trace` script: unknown sections and lines are an error everywhere; missing citations are an error in the kernel and a report elsewhere; a reverse map (section → code → refcore → T tests) and the uncovered sections printed for each milestone**;
- (c) (b) plus T's tests carrying `//@ spec: L §n` headers, as the Rust Reference's tests do.

*Pick (b)*, with (c) offered to T's author, since T's tests are T's.
*Cost:* E low to medium (about 150 lines of Python); R high (the owner audits by section); S none; K: citations that are true but too coarse. The reviewer checks that the cited section says what the code does (BUILDER §12 item 1).

**D5-5. The owner's audit kit.**
*Problem:* the owner must judge each milestone without reading Rust, and must read little.
*Options:*
- (a) the reviewer's verdict only;
- (b) **a generated milestone page plus a readability section in BUILDER §12's checklist**;
- (c) (b) plus an "explain this module" prose file per module.

*Pick (b).* The page lists: modules added and changed with their purpose lines; spec coverage delta; new exceptions with reasons; size, nesting and clone deltas; benchmark deltas; new fences.
The checklist adds:
- every new file has its header;
- citations match the code;
- no unlisted `dyn`, generic, macro or trait;
- each fence has its benchmark and twin test;
- names are the spec's words;
- no duplicated block over about 10 lines.

What the owner reads: `ARCHITECTURE.md` at S; then, per milestone, the one page and the reviewer's verdict; refcore and the spec for any module they want to check.
*Cost:* E low (it reuses `advisory`, `exceptions`, the trace and the benches); R high; S none; K: (c) goes stale, so it is not recommended (M-NO-META-DESIGN-DOCUMENTATION [S10]).

**D5-6. Fencing performance code.**
*Problem:* performance is core, but clever code spread everywhere is unreadable and often doesn't pay.
*Options:*
- (a) no rule;
- (b) **performance work lives in named fence modules, each with a `PERF:` header, a benchmark, a plain twin and an equivalence test; `#[inline(always)]` and `#[cold]` are reported outside fences**;
- (c) (b) plus a ban on any optimisation before gate 12's first benchmark run.

*Pick (b).* Plain code first, and a fence only when a benchmark row asks for it. The fences expected from `shape.md`: walk skipping and checkpoints, memo, read index, `Num` tiers, threads.
*Cost:* E medium (a benchmark and a twin per fence); R high (unreadable code is boxed and explained); S: no loss, since the gains come from structure [S31]; K: a fence's plain twin costs build time. Keep the twin only where cheap, and refcore is the twin of last resort.

**D5-7. Readable strictness.**
*Problem:* R-5, R-19 and R-21 turn every `i + 1`, `x[i]` and `as` into longer code, which an LLM may shorten in ways that hide a rule.
*Options:*
- (a) write `checked_add(…).ok_or(…)?` everywhere;
- (b) **domain newtypes with checked methods first, named helpers in one kernel module second, iteration instead of indices; no arithmetic macros and no operator-like extension traits**;
- (c) (b) plus one extension trait on the integer types.

*Pick (b).* Each helper's doc names the rule it serves (`R-19`), the `?` stays at the call site, and the helper module sits in the mutation kernel.
*Cost:* E low; R gain; S none, since newtypes are elided [S33]; K low. (c) blurs project and std methods.

## Unknowns until the engine runs

1. Whether nesting at 5 fits the lexer, the parser and the stratified day walk, or calls for exceptions. Only the first 2 000 lines will tell. Re-judge at S with the exception count.
2. Whether an LLM, bound by a nesting cap, extracts helpers well or splits mechanically. The milestone review's duplication and nesting deltas will show it.
3. The real cost of R-19 and R-5 in the walk's inner loop on this engine. Readyset's "negligible" is another workload. Gate 12's benchmarks settle it, and if they don't, a fence is the answer.
4. Whether `enum` dispatch beats every alternative for the expression evaluator, against, say, a compiled closure tree. That is a fence question for the benchmarks, not a style rule.
5. Whether section-level citations are fine enough. Some LANGUAGE sections run over 100 lines. The `l.N` form exists for precision, and whether reviewers need it is unknown.
6. Compile-time effects of the subset: fewer generics should build faster [S3], unmeasured here.

## Contradictions with phase 1, and spec observations

- **The advisory thresholds disagree.** The scaffold's `tools/advisory.py` reports length at 60, cognitive complexity at 20 and nesting at 4. A5 SC-6 proposed 100 and 6, and RULEBOOK R-74 names no numbers. D5-3 fixes them.
- **K-21 is revised in part** (D5-3): nesting becomes an error. Phase 1's A1 had proposed exactly that, at 5.
- **The complexity group is already on.** `too_many_arguments` and `type_complexity` are errors in the scaffold through the denied `complexity` group, and the rulebook doesn't list them. They are not wrong, just undocumented to the owner. `excessive_nesting` is in the same group, so setting its threshold makes it an error with no lint-table change.
- **R-73 (macros, report) would become an error** under RS-6. That is a rules change, through R-112.
- **R-75 (citations, report) would become an error in the kernel** under D5-4.
- **Microsoft's guidelines differ from the rulebook in two places, by design:**
  - M-PANIC-ON-BUG ("detected programming bugs are panics") against R-3, R-4 and BUILDER §5's `ENGINE-INVARIANT`;
  - M-FROM-ERROR ("canonical error conversion uses `From`, not `map_err`") against R-66's allowed `map_err(|_| …)`.

  Phase 1's choices stand. They are noted so a reviewer who cites those guidelines knows.
- **The spec has no paragraph ids.** The Reference has `r[…]` rule ids and the FLS has paragraph ids, while Tally's spec has only section numbers and lines. Since the spec is frozen, `§n.m` plus `l.N` is stable. This is noted, not fixed.
