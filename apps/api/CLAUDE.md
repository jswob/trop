# API Application

Elysia API server with PostgreSQL database via Drizzle ORM, Pino logger, dev port 3001.

## Key Patterns

- **Migrations**: `drizzle/` holds migration files — generated by the user only.
- **Module factory**: each module exports `create[Name]Route(db)` returning an Elysia instance with a prefix.
- **Shell and routes**: `src/index.ts` is the shell (logger, CORS, the security guard, sign-in, wake, `/health`, the `App` type). The app's modules are composed with `.use()` in `routes(db)` in `src/routes.ts`; work beside the requests starts in `startBackground(db)` there (none yet). A token in `?token=` counts only on `queryTokenPaths` (for a route an `EventSource` reads; none yet); everywhere else only the `Authorization` header does.
- **Service layer**: complex business logic is extracted into `service.ts` files within modules. Services accept a `DatabaseConnection` and return `ServiceResult<T>`. Route handlers call services and map results to HTTP responses via `mapError()`.
- **ServiceResult**: discriminated union with `ok(data)` / `fail(code, message)`. Codes: `NOT_FOUND` | `VALIDATION` | `CONFLICT` | `INTERNAL`. `VALIDATION` is used both for input validation and state-guard errors (a write the record's state does not allow).
- **Database injection**: all route factories accept a `DatabaseConnection` parameter for testability. Tests provide an auto-rollback transaction; production uses the real connection.
- **Schema conventions**: define tables in `db/schema/[name].ts` using shared columns from `common.ts`. Export types with `InferSelectModel`/`InferInsertModel`. Always re-export from `schema/index.ts`.
- **Database tooling**: snapshots, the safe push, test and e2e setup and the pre-commit schema check are the `drizzle-snapshots` CLI (`@jswob/drizzle-snapshots`). This app's side is `drizzle-snapshots.config.ts`: its database names (`src/db/target.ts`), migrate and seed scripts, raw constraints, and schema folders; add a folder there when the schema imports from a new one.
- **Seeding**: `db:seed` empties the seeded tables and loads the newest snapshot of real data from `src/db/seed-data/` (not committed). `src/db/seed-core.ts` is the generic loader; `src/db/seed-tables.ts` is this app's part: `SEED_TABLES` in insert order, `ALSO_CLEAR`, and `seedFallback`, which seeds two sample notes when there is no snapshot. A new table that holds real data goes into `SEED_TABLES`.
- **Type exports**: `@app/api/types` maps to `src/db/schema/index.ts`. Other packages import types via this export.
- **Shared validation schemas**: a TypeBox schema more than one module takes lives beside its owner and is imported from there.
- **Idle means silent**: with nothing happening, the API sends the database nothing — no timer may query on a tick, and `/health` (asked by Fly every 10 s) never touches it. Fly suspends the idle machine and Neon scales to zero, and both rely on it: a poll keeps the database awake and leaves connections open across a suspend. Background work is woken by what causes it, never by a timer.
- **Prepared statements**: `db` sends every query prepared (`withPreparedStatements` from `@jswob/drizzle-utils`); `DATABASE_PREPARE=false` turns it off.
- **Query count**: the number of statements a request sends must not grow with the rows it handles — no query inside a loop or a per-row helper, independent reads in one `Promise.all`, one write per table and kind of change (`caseBy` from `@jswob/drizzle-utils` for per-row values). The API skill's `QUERIES.md` has the patterns.

## Module Types

- **Simple**: `index.ts` (route handler) + test file — direct CRUD, no service layer needed.
- **With service**: adds `service.ts` for business logic extraction. Route handler delegates to service, maps `ServiceResult` via `mapError()`.
- **Complex**: adds specialized files beside the service — a background task, an event emitter, a client for another service.

**Notes** (`modules/notes/`) is the example resource, a module with a service: copy its shape for the app's first one. `docs/removing-notes.md` at the repo root lists every file it takes, so an app removes it in one commit.

## Testing

- Import `{ test, expect, describe }` from `src/test/test-context.ts` (never from vitest directly).
- Context provides `tx` (auto-rollback transaction), `factory` (bound fixtures), `db`.
- Fixtures: one file per table using `createFixture()` from `@jswob/drizzle-fixtures`, composed via `composeFactory()` in `test/fixtures/index.ts`.
- Tests collocated as `[name].test.ts`.
- `countQueries(run)` from `src/test/db.ts` counts the statements a call sends; list endpoints, nested reads and multi-row saves get a query budget test showing the count is the same for little data and for a lot.

## Database Commands

All commands run from the monorepo root:

| Command                  | Description                                                                             |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `bun db:up`              | Start PostgreSQL container                                                              |
| `bun db:down`            | Stop PostgreSQL container                                                               |
| `bun db:push:safe`       | **ALWAYS USE** — push schema with auto-snapshot                                         |
| `bun db:push`            | Push schema (no snapshot — avoid)                                                       |
| `bun db:generate`        | Generate migration (**USER ONLY** — never run this)                                     |
| `bun db:generate:custom` | Create empty migration file (**USER ONLY**)                                             |
| `bun db:migrate`         | Run pending migrations                                                                  |
| `bun db:migrate:status`  | Check migration status                                                                  |
| `bun db:seed`            | Load the newest data snapshot (`src/db/seed-data/`); without one, change nothing        |
| `bun db:base`            | Create protected baseline snapshot (never auto-deleted)                                 |
| `bun db:snapshot [name]` | Create instant snapshot (auto-rotates old ones)                                         |
| `bun db:snapshot:list`   | List all snapshots with status                                                          |
| `bun db:restore [name]`  | Restore from snapshot (latest if no name)                                               |
| `bun db:reset`           | Return to protected baseline                                                            |
| `bun db:undo`            | Revert last push instantly                                                              |
| `bun db:clean`           | List this project's snapshots and backups; `--force` restores baseline and removes them |

**Snapshot workflow** (every snapshot volume starts with `COMPOSE_PROJECT_NAME`, so projects on one
machine never touch each other's; `postgres_snapshot_*` volumes from before that are listed by
`db:snapshot:list` and left alone):

- Run `bun db:base` before major experiments
- Use `bun db:push:safe` during development (auto-snapshots before each push)
- Use `bun db:undo` or `bun db:reset` on failure
- Snapshots copy a whole volume, so one taken under Postgres 16 restores a volume Postgres 18 will
  not start on (`README.md` says how to move to 18)
- NEVER run `bun db:generate` — only the user creates migrations
